# HELIX-OS基盤化・上流取込指示書

対象: RetryYN/HELIX-HARNESS内のHELIX-OS新世代要求。目的は、以下を単発の補助agentではなくOSの共通基盤として要求化し、設計・実装・検証へ導出可能にすることです。

照合基準: docs/l2-requirements-source-audit@eed31df2f04bdb5973cd07176770ee5855528328（2026-09-14確認）。着手時は最新HEADと差分を再取得してください。本書は上流取込指示であり、個別revisionの承認・実装起動・外部操作の包括許可ではありません。

## 1. 固定する構造

人間の意図・承認済み要求の下に管理知能を置き、その配下に推進知能と検収・収束知能を置きます。管理と配下、推進と検収は双方向通信します。許可範囲内の相談・調整は直接行い、管理を全通信の中継点にしません。役割の分離を固定3モデル・3プロセス・3サービスへ変換しないでください。

管理は全体目的、優先順位、依存、担当、予算、投入量、停止・再開、是正先を統制します。推進はチケットを設計・実装・成果へ進めます。検収は単なるreviewerではなく、チケット・設計・実装差分・現在の統合先から、適切なマージ順序、統合単位、必要な検証・CIを算出し、実行させ、結果に応じて再計画して収束させます。reviewerとCI runnerは検収が利用する実働資源です。

HARNESSは工程・V-pair・検証義務・完了条件を所有し、OSは適用・実行・記録・統制を所有します。個別製品の要求意味をOSへ吸収しません。

## 2. チケットから降ろす

指示・観測・改善候補を管理が整理し、repo-ownedチケットを発行します。要求revision、成果、scope、主責任者、依存、workflow契約、受入、許可操作、予算・期限・停止条件を束縛して配下へ降ろします。GitHub Issue/PRは参照・協調・証拠の投影先であり、要求正本ではありません。

推進・検収は許可済み枠内で子作業を割当できるようにし、親子の予算・責務を保存します。scope・優先度・workflow・共有資源の変更は提案として管理へ返します。承認要求の意味変更は対象上流の判断へ戻します。workflow再選択時も既存の未完義務を失わせません。

## 3. 実働機構

- Agentic Worker: 調査、分解、設計、実装、testを有界に遂行。探索は可能ですが要求・権限を自己拡張しません。
- Patch Bot Worker: 正解・変更範囲が既存契約から確定する限定修復。検収から直接利用可能。行数で分類せず、設計選択が必要なら推進へ返します。修復者と最終検証者は分離します。
- System Info Crawler: 内部の要求、設計、code、branch、依存、設定、runtime、CI、担当をread-onlyで観測し、出典・revision・時点・取得範囲・欠落を返します。
- Tech Web Crawler: 内部の解決事例を先に照合し、不足分をGitHub Issue/PR/commit/test、公式文書、技術記事から調査します。症状だけでなく原因構造を照合し、修正・検証・未解決点・適用条件・相違・出典・版を返します。closedやmergedだけで解決認定しません。
- Semantic CI: 検収の検証計画・実行機構。要求・設計・実差分から検証義務を具体化し、runnerへ配車、監視、回収します。LLMの裁量で必須検査を削らず、不明をskipにしません。

以上は本構想の役割名です。特定製品・provider・言語の採用指定ではありません。

## 4. 統合と検証

意味trace、着手依存、統合順序、実行eventを別関係として扱います。ファイル競合なしを独立の証明にしません。A→Bなら実際のbase+A+Bを統合候補として検証し、base更新・候補追加削除・順序変更時は影響を再計算します。

必須検証集合、選択理由、非適用理由、残義務をHARNESS契約に照合します。影響範囲が証明不能なら承認済みの保守的検証へ戻し、それでも義務を確定できなければ停止します。内容検証、独立review、merge admission、release、運用評価を分け、review待ちだけで安全な内容検証を止めません。

証拠は対象commit/tree、要求・HARNESS・policy・oracle・環境・実行世代へ束縛します。管理記録の追加で検証対象HEADを書き換えず、流用は有効性を証明できる範囲だけ許可します。実mergeは実行境界が直前再検証し、統合先の更新とread-afterを確認します。

## 5. 全体を包むログ・診断

管理・推進・検収・worker・crawler・CIを同じ仕事のIDで関連付けます。入力revision、判断要約、期待結果、操作、実結果、時間・費用、因果参照を保存し、観測事実・AI仮説・承認・表示を区別します。

トップダウンで要求→チケット→設計→実装→検証→統合の欠落を探し、ボトムアップで失敗・停滞・手戻りから原因候補を辿ります。両者を突合し、直す層・対象・根拠・確度・影響・担当候補・改善確認方法を管理へ返します。管理自身も是正対象です。

診断は自動writeせず、管理が重複排除・優先度決定・是正チケット化します。修正後は元の症状と退行を再観測し、解消確認まで閉じます。ログがない未着手と観測停止も検出し、欠測を正常に変換しません。

## 6. 共通の実行・通信境界

各知能に別正本・別scheduler・別承認制度を作りません。typed JSONで対象revision、送受信者、因果ID、期限、根拠を伝え、提案・指示・結果を区別します。単一writerは対象単位とし、無関係な仕事まで直列化しません。

実行直前の権限・scope・lease/fence・世代確認、CAS、冪等性、再試行上限、永続記録、replayを要求します。Git/DB/GitHub全体を一つの原子transactionと仮定せず、部分失敗・結果不明からの再照合と回復を設計してください。

外部情報は未信頼データです。秘密の検索送信、取得文中の命令実行、外部patchの自動採用を禁止し、出典・利用条件・再現検証を要求します。診断や検証器自身の修正も独立検証します。

## 7. 既存上流への接続と成果物

Concept v4.1、OS L1/L2/L11、新世代CI候補、上流再整備方針・backlogを照合してください。主な接続先はHELIXOS-L2-001〜005/007〜009とNCI-OS-001〜008です。既存IDを入口に具体化し、責務が独立する新要求だけ新IDを提案します。既存の正規V-pairを維持します。

まず要求差分、責務・権限表、入出力契約候補、L11受入シナリオ、L3/L10への導出表、段階計画を提出してください。U1〜U4の上流確定後にのみU5設計実装→U6切替→U7退役へ進みます。起草・承認・検証・実装の状態を分け、記録の不一致を先に解消します。

旧CI・runtime・AI文書は意味・失敗事例の参考に限定し、実行baseline・parity・fallbackにしません。上流整理中の旧CI起動、実装、PR作成、merge、branch削除は行いません。ブランチは最新HEAD・差分・未移管義務・利用者を分類し、削除を先行しません。

必須受入: 双方向調整、A→B統合と再計画、必要CI欠落拒否、限定修復と独立再検証、未着手検出、障害から上流是正、外部事例の検証採用、再起動・二重配送・stale拒否、管理自身の是正、効果の再観測を一周で示すこと。詳細は02、取込候補は03を参照してください。
