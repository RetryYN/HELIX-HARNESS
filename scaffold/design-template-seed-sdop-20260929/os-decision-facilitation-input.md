# HELIX-OSの「決める事項の司会進行」への入力（要求候補を起こす前の材料）

status: research_scaffold（材料の整理。要求の採否、L1・L2の改訂、設計の決定ではない）
authority_effect: none

## この材料の位置

POは2026-09-29に、WBS系の「決めるもの」をHELIX-OSに載せ、OSが司会進行できるようにしたいと述べた。さらに、目的別の手法を組み合わせ、OSがHARNESSと連携して「どこまで決めるか」を扱いたいと述べた（原文：[decision-facilitation-po-original-2026-09-29.md](../../docs/helix-os/sources/decision-facilitation-po-original-2026-09-29.md)の発言1〜3）。

本書は、プレイブックの`references/07-process-and-roles.md`、`references/06-aws.md` §3、`assets/template-raci-open-issues.md`、`assets/template-adr.md`から、この意図に当たる意味atomを抜き出して並べる。要求候補にするときは、下の「既存候補との関係」を照合し、POの採否を経る。

### A. 何を決めるかを洗い出す（HARNESS・BRAINの材料をOSが使う）

| atom | 出典 | 行き先の見立て |
|---|---|---|
| A1 「何を決めるか」はチェックリスト（フレームワーク）で、「いつ・誰が・どの順で」はWBSで導く。WBSだけから始めると、作業の抜けは見つかっても決めるべき論点の抜けに気づきにくい。先に論点を網羅する | 07 §1 | OS進行の順序（論点の網羅 → WBS）。論点の中身はDesign Template |
| A2 論点を洗い出す枠：IPA非機能要求グレード、AWS Well-Architected、AWS CAF（ビジネス・人材・ガバナンス・プラットフォーム・セキュリティ・運用）、推奨構成との差分（Security Reference Architecture／ランディングゾーン）、ISO/IEC 25010、ユーザーストーリーマッピング | 07 §2、PO発言3 | BRAINのtemplate候補（DT-SDOP-002、006等）。CAF・ストーリーマッピングは本seedに未収録（後続候補） |
| A3 フェーズ表の「決めること」が、ほぼそのままWBSの上位項目になる | 07 §1 | 論点 → 作業への変換。WBS-OS-001の入力 |

### D. いつ・どこまで決めるか（決める時期と深さ）

| atom | 出典 | 行き先の見立て |
|---|---|---|
| D1 戻れない判断（一方通行のドア）は早めにじっくり、戻れる判断（両開きのドア）は必要になるまで遅らせて素早く。全部を最初に決めると、情報不足のまま決めて手戻りが増える | 06 §3、SKILL.md軸2 | OSが論点ごとに「決める時期」を割り当てる規則の候補 |
| D2 フェーズごとの深さ：企画は方向性、要件定義は数値で合意、基本設計は後から変えにくいものを確定、詳細設計はパラメータ（仮の値でよい）、構築・試験は実測で決め直す、運用は継続的に見直す | 06 §3 | HELIXの層（L1〜L3、設計、検証）へ対応づける候補。層の対応は未照合 |
| D3 早く決めすぎないもの（サイズ、長期割引、閾値）は「仮の値で始めて見直す」と決めること自体が正しい決め方 | 06 §3 | 未決事項の状態に「仮の値で進行・見直し条件付き」を持たせる候補 |

## 対象外とする候補（採らない理由）

| atom | 出典 | 理由 |
|---|---|---|
| 工程ごとの担当（発注者、ベンダーのPM・SE等）と契約形態（請負・準委任） | 07 §6 | 日本のSI案件の人の体制と契約であり、HELIXの工程の担い手（レーン、Worker、PO）と対応しない。法的な判断を含む。「要件定義の主体は発注者」は、HELIXでは「要求はPOが持つ」（自律境界）として既にある |
| WBSの例の日数・担当名 | 07 §1 | 例示であり、見積もりの規則ではない |

## 2026-09-30に受領した外部見解（POが会話へ貼付、要旨）

POは、上の材料を「決め忘れ・リスク・検証不足から必要な作業を導くWBSエンジン」にする方向の外部見解を貼り、Claudeへ意見を求めた。採否は未判断である。見解の要旨と、本材料との対応は次のとおり。

| 見解の要点 | 本材料との対応 |
|---|---|
| 手法ごとに、適用条件、必要入力、確認する問い、期待する成果物、完了を示す証拠、責任者、参照資料の版を持たせる | DT-SDOP-001〜007が持つ契約の項目（適用条件、必須入力、negative oracle、完了条件、出典）と同じ形。手法もtemplateと同じ契約で持てる |
| 手法ごとの出力をWBSへつなぐ（ストーリーマッピング・ISO/IEC 25010 → 要求の抜け、STRIDE・FMEA → 対象と反例が明確な作業、RACI・未決事項・比較表・ADR → 判断と判断待ちの作業、SLO・PoC・性能試験・障害訓練 → 計測と合否の証拠、AWS CAF・SRA → 案件条件に応じた追加の論点） | A〜Eの意味atomと同じ並び。F1の流れ（論点の網羅 → 深掘り → 決め方 → 試して決める → WBS）に当たる |
| 不明なことを埋めてWBSを完成させるのではなく、不明なことを解消する作業をWBSに入れる。「決まっていない」と「作業を忘れた」を区別する | D3（仮の値で進行・見直し条件付き）、C2（未決事項リスト）を、WBSの作業として持つ形 |
| 同じ問題が複数の手法から出ても、対策を重ねて起票しない。元の論点は残し、共通の作業・成果物・検証へ関連付ける。有効な既存の判断・検証結果は再利用する | 未決1（未決事項・リスク登録簿を別台帳にするか、WBS台帳の作業kindにするか）を決めるときの条件になる |
| 実際の証拠で計画を育てる（PoC・プロトのログで試し、見つかった不足から要求・設計・試験とWBSを更新する） | E4（PoC・プロトへのログ差し込み）。既存のPoC／Discovery／Backflowの経路を使い、別の工程を増やさない |
| 担当：手法の知識・雛形はBRAIN、適用規則と設計・検証義務はHARNESS、案件への適用案はINTELLIGENCE、ticket発行・担当・進行管理はOS、効果評価はLABO | 現行Conceptの機構の役割（OSは工程管理、BRAINは設計導出、INTELLIGENCEは支援、HARNESSは開発実行基盤）と合う |
| 要求を洗い出す段階から使い、その結果をWBS生成へ引き継ぐ | A1（WBSより先に論点を網羅する） |
| 導入は、未決事項・責任者・判断記録の接続を先に整え、品質・リスク分析とPoCへの接続を一つの案件で試す。評価は手法数・タスク数ではなく、見逃し、手戻り、判断待ち、検証を含む総工数で行う | 評価はLABOの責務 |
| 境界：手法から出た指摘を自動で新要求へ昇格させない。比較表の高得点で安全・権限の必須条件を相殺しない。RACIの担当指定を操作許可にしない。既存承認内の作業に毎回の人間再承認を足さない | C1・C4の注記、ADD-02の補正文言（2026-09-29 PO判断）と同じ境界 |

要求候補へ起こすときの注意：
- `wbs-ledger-requirements.md`は、現段階でWBSエンジン・schema・DB・GitHub連携を実装・起動しないとしている。本見解は要求の意味の材料であり、この禁止を変えない。
- AWS CAF・SRA等の分野別の論点は、案件の条件で適用する。Web展開後に扱うSecurity・インフラの内容を1.0の必須条件へ前倒ししない。

## 未決（要求候補へ起こすときにPOへ確かめること）

1. 未決事項リストとリスク登録簿を、WBS台帳とは別の台帳にするか、WBS台帳の作業kindにするか。
2. 製品の設計判断のADRを、どの機構のどこへ置くか（HELIX-HARNESS-COREの設計記録か、OSの登録か）。
3. RACIのAに、PO以外（例：レーン）を置いてよい判断の範囲。旧HELIXの自律境界（要件の起草以下はAIが自走）を基準にしてよいか。
4. D2の「フェーズごとの深さ」を、HELIXのどの層へ対応づけるか。
5. 発言4（PoC・プロトへのログ差し込み）を、1.0の工程にするか、後の版にするか。
