### 不成立例（negative oracle）

- 最優先の4項目（アカウント構成、リージョン、VPC CIDR、IaCツール）を決めずに、構築を始める。
- ルートユーザーにMFAがない、アクセスキーがある。人の長期アクセスキーを常用する。
- 操作記録（CloudTrail）を組織全体で有効にせず、改ざん防止の保管先がない。
- ログの保存期間を既定（無期限）のままにする。
- 予算アラートがない。
- 通知の受け手（アカウント管理者、セキュリティアラートの確認者、費用の確認者、障害時の連絡体制）が決まっていない。
- 後から変えやすいもの（インスタンスサイズ、長期割引、アラームの閾値）を、実測なしに最初に確定する。

### 完了条件

§1〜§5の項目に、決定値・決定者・根拠（ADR）がある、または理由付きN/Aである。§6の「早く決めすぎないもの」は、仮の値と見直しの時点が書かれている。

## 設計の要点

- AWSで楽になるのは物理運用とマネージドサービスの範囲。楽さは「どこまで任せるか」で決まる（EC2＜Fargate＜Lambda）。
- 責任共有モデル：AWSが守るのは基盤。その上の設定・データ・アプリは利用者の責任。
- AWS自体の更新（ランタイム、DBエンジン、Kubernetesの版）にもサポート期限がある。EOL管理（DT-SDOP-005）の対象に入れる。
- 従量課金のため、ログの出しすぎ・消し忘れはそのまま請求になる。
- 後から変えにくい順に決める。最優先の4つは後から変えると移行作業になる。

## 本体

### 1. 最優先（後から変えにくい）
- AWS Organizationsの構成（OU、アカウント一覧：管理／ログ保管／監査／本番／ステージング／開発／サンドボックス）
- ランディングゾーン（Control Tower等）の採用有無
- リージョン（メイン／DR）とデータ所在地
- VPC CIDRの割当て表（既存・オンプレ・将来分と重複しない）
- サブネット構成（パブリック／プライベートApp／プライベートDB × AZ数）
- IaCツールとstateの管理方法、手作業でのリソース作成の禁止

### 2. セキュリティ（初日）
- 全アカウントのルートにMFA、アクセスキーなし
- 人のアクセスの一元管理（IAM Identity Center）、MFA必須、CI/CDはOIDC
- SCPによるガードレール
- CloudTrail組織証跡 → ログ保管アカウント（改ざん防止）
- GuardDuty／Security Hub／AWS Configの有効化
- S3のブロックパブリックアクセス（アカウント単位）
- 保存時暗号化の既定、鍵の方針、秘密情報の保管先

### 3. 運用
- 命名規則、必須タグ（Project／Environment／Owner／CostCenter／ManagedBy）
- コンピュート方式と理由（ADR）
- データストア方式・マルチAZ
- ログの保存期間（全ロググループ）
- アラームと通知先
- バックアップ計画（頻度・保持・別リージョン／別アカウントへの複製）
- CI/CDと本番デプロイの承認フロー
- ランタイム・エンジンの版のEOL管理

### 4. 費用
- 予算アラート（実績80%・予測100%等）
- 費用配分タグ、費用の異常検知
- 開発環境の夜間停止
- 長期割引は利用が安定してから検討（見直しの時点）

### 5. 体制
- AWSアカウントの管理責任者
- セキュリティアラートの確認者
- 費用の確認者と頻度
- 障害時の連絡体制

### 6. 早く決めすぎないもの
| 項目 | 仮の値 | 見直しの時点（実測の条件） |
|---|---|---|
| インスタンスサイズ・DBの性能クラス | | |
| 長期割引 | | |
| アラームの閾値 | | |

### 7. 設計レビューの観点
Well-Architectedの6本柱（運用上の優秀性、セキュリティ、信頼性、パフォーマンス効率、コスト最適化、持続可能性）で見直す。
