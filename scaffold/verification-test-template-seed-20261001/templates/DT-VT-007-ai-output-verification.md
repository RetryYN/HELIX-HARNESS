### 不成立例（negative oracle）

- 成果物を作ったAIが書いたtestだけで合格とする（同源化）。
- 構造の検査がgreenであることを「品質を保証した」と書く。
- 作成に関わったmodel・sessionが、同じ成果物のreviewを担う。
- 攻撃が成立しなかったこと（no_attack）を、安全の証明とする。
- 出典を示さない事実の主張を、確かめずに採る。

### 正例と境界の負例

- 正例：AIが書いた判定ロジックについて、L5設計から別のsessionで先に作ったhidden test（C37）で確かめ、独立review（C36）の指摘を0件にした。
- 境界の負例：軽微な文言の修正で、hidden testを省いた。省いた理由を`omitted_checks`に書けば成立する。書かずに、作成したAIのtestだけで合格とするのは不成立。

### 完了条件

成果物の種類ごとに、観点（§1）の確認結果と、機械の検査と独立reviewの結果が分けて記録されている。作成に関わったmodel・sessionと、reviewの担い手が別であることが記録されている。**完了条件を満たしても、要求の合意・承認・受入にはならない。**

## 本体

### 1. 観点

| 観点 | 内容 | 結果 |
|---|---|---|
| 正確性 | 事実・仕様と一致するか | |
| 幻覚 | 存在しない事実・APIを作っていないか | |
| 根拠・出典 | 参照した情報源が正しく、古くないか | |
| 一貫性・完全性 | 前後の矛盾、抜け漏れがないか | |
| 安全性 | 権限・tenantの逸脱、破壊的な操作、有害な出力がないか | |
| 機密・PII・license | 秘密・個人情報の漏れ、著作権・licenseの違反がないか | |
| 偏り | 不公平・偏りがないか | |

### 2. 流れ

AIの生成 → 機械の検査（test、lint、schemaの検証、事実・出典の確認） → 独立review → 記録。不合格は修正の指示（再生成）へ戻す。

| 成果物 | 機械の検査 | reviewで見ること |
|---|---|---|
| code | test（hidden testを含む）、lint、静的解析 | 設計の意図、読みやすさ |
| 設計文書 | 形式・参照・traceの検査 | 内容の妥当性 |
| 文章・回答 | 事実と出典の確認 | 正確さ |
| データ・分類 | schemaの検証、sampleの確認 | 代表性、偏り |

### 3. 3つの層

| 層 | 手段 | 見つけられるもの | 残るもの |
|---|---|---|---|
| 構造の検査 | 形式・参照・traceの機械検査 | 参照切れ、閉包漏れ、型の不一致、証拠の欠落 | 検査を通すためだけの形式的な記入 |
| 敵対的な検証 | 反例を作る側と、根拠で反駁する側を分け、反駁されない反例が1つでもあれば指摘にする。両者は別session・可能なら別model、作成に関わったmodelは就かない。資料だけを渡し、作成の経緯を渡さない | 判定できない要件文、testが覆わない境界、確かめられない証拠 | 弱い攻撃、無理な反駁、model共通の盲点 |
| 人の確認 | 独立reviewと、人の上流判断（Concept、企画、要求、要件の承認） | 上の層が見逃す種類の欠陥 | 頻度の低さによる取りこぼし |

報告では、greenやpassを「品質を保証した」と書かず、「構造の整合を保ち、独立の検証に耐えた」と書く。
