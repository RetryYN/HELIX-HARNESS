### 不成立例（negative oracle）

- 要件の一部だけに行があり、行の無い要件を「対象外」と書かずに落とす。
- 1つの要件に方式だけを書き、対・技法・caseを書かない。
- 非機能に「十分に速い」「安定している」のような測れない書き方をする。
- 開始・完了の基準に、CI greenやmergeを完了として書く。
- 技法の数・case数・coverage%を、検証の十分さとして書く。

### 正例と境界の負例

- 正例：要件「負債の件数が前回を超えたらfail」の行に、方式＝テスト、対＝P5、技法＝C04（前回値の9・10・11件、前回unknown）、case ID、oracle IDを書いた。
- 境界の負例：同じ要件で、前回値がunknownの場合の行を書かなかった。境界の区間が欠けているので不成立。行を足すか、理由付きでN/Aにする。

### 完了条件

対象の要件の全件に行があるか、理由付きのN/Aである。各行が方式・対・技法・case ID・oracle IDを持つ。非機能は測れる形で書かれている。**完了条件を満たしても、検証の合格・要件の成立を意味しない。**

## 本体

### 1. 検証の方式

| 方式 | 内容 | 主なカード |
|---|---|---|
| テスト | 実行して期待結果と比べる | C04〜C35 |
| レビュー・検査 | 設計・コードを静的に確かめる | C01、C03、C36 |
| 分析 | modelや計算で妥当性を確かめる（性能の試算等） | C30の事前見積り |
| 実証 | 実環境で動作を示す（受入） | C08、C26 |

方式は組み合わせてよい。1つの要件に方式を1つだけ書く必要はない。

### 3. 網羅の観点（数値は置かない）

| 観点 | 何を満たせば網羅とするか |
|---|---|
| 要件 | 全要件に行がある（本表） |
| 同値・境界 | 各区間・各境界に最低1件 |
| 状態遷移 | 全状態・全許可遷移と、禁止遷移 |
| デシジョン | 全規則（列） |
| 構造（code coverage） | 未実行の変更行の発見に使う。合格の閾値にしない（C09） |

### 4. テストデータ

- 正常・異常・境界・空・最大のパターン。権限・tenantを分けて確かめる対象では、複数の権限・tenantを用意する。
- 本番相当のデータを使う場合は、個人情報・秘密情報を除く。
- seedを記録し、同じデータを再現できるようにする。繰り返し実行しても結果が変わらないようにする。

### 5. riskによる配分

影響と起こりやすさでriskを評価し、高いところに技法を厚く配分する。低いところを減らすときは、省いた検査を`omitted_checks`に記録する（DT-VT-001、HARNESS-L2-005）。

### 6. 開始と完了の基準

| 対 | 開始（入力がそろっている） | 完了（証拠がそろっている） |
|---|---|---|
| P6 L6↔L7 | 対の設計が凍結済み、oracle IDがある | Red→Greenの記録、原子CIの結果 |
| P5 L5↔L8 | Provisionalの成果物、L5詳細設計 | L5との照合結果、未解決の指摘0件または戻し先の記録 |
| P4 L4↔L9 | P5の証拠、L4基本設計、コネクタの契約 | 境界の照合結果、失敗の伝わり方の確認 |
| P3 L3↔L10 | 下位の証明のreceipt、L3要件 | システムに固有の義務の差分の確認 |
| P2 L2↔L11 | Verifiedの成果物、L11受入の条件 | 人の受入の記録（本templateは受入を作らない） |

完了の列は、成果物の状態を上げる判定ではない。状態の遷移はHARNESS-L2-022の契約による。
