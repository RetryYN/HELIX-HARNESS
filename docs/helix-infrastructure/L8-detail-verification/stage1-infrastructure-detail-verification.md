# HELIX-INFRASTRUCTURE Stage 1 詳細検証設計

本書は[対のL5詳細設計](../L5-detail-design/stage1-infrastructure.md)の検証fixtureと期待oracleを定める設計候補である。L4/L9の固定意味・40個のL9 verifier ID、L3/L10の全体pin、親scope、owner境界を維持する。fixtureは合成入力の構造と結果分類を定めるもので、実sourceの存在、物理状態、実行、authority、復旧結果、測定合格を生成しない。

## 1. 固定入力と実施境界

L5本文SHA-256はfrontmatterの`paired_l5_sha256`に固定する。L5が固定するL4 SHA-256は`84756e019c04744ede7825518e4a153f1373260df1b972c5651ade7824ab9dec`、L9 SHA-256は`b83eee2452ec0b41ef23ffd6a3aea3e1374f82dbffc3e8c7bb54908b01ae9d8b`。L4/L9の固定対象はL3/L10六本文全体であり、機能親は`HELIXINFRASTRUCTURE-L2-001`と`HELIXINFRASTRUCTURE-L2-006`の2 identity、L2-005は006の適用復旧義務を読む入力依存に限る。

L4/L9で定義済みの40行は、001の15 verifier、006の19 verifier、NFRの6 verifierから成る。下表はその全IDを一つずつ対応付け、各正常fixtureと単独変異、oracleをL5のcomponent/API境界へ詳細化する。行内の「別fixture」「一つずつ」は、それぞれ独立した入力変異であり、複数欠陥を同時に入れない。

合成fixtureは既存K2 `SubjectRef`/`ResultKey`、K6の読取観測、K3 permission query/check、K5 evidence参照と、必要な場合のK7 generation pointer/EpochToken fencing inputを使う既存契約の入力として表す。OS operation/attempt observation refsはOS ownerが既存宣言している場合だけ使う。値、identity、revision、ownerはfixture内だけのデータであり、製品schemaや新しいowner/permission/APIを定義しない。fixtureで使うauthorityは既存型の入力参照として与え、authority記録・可否・有効性をこのpairで作らない。

すべてのcaseで、reader/operation adapter/Worker/CONNECT/SECURITY/OSへの実呼出しは行わない。`prepare_operation_check`等のL5境界は入力の構成と期待値の照合対象であり、対象operationを開始しない。L10の技術候補値もfixtureに与えられたときの比較条件であって、実測値、実装値、SLO、L3追加承認ではない。

K1結果は共通kernelで既に定義された値型と理由だけで表す。K1に`missing`というclass/reasonはない。完全走査で必要対象の不存在が確定した場合は、当該既存domain valueのabsenceとして`Value`に保持し、polarityは既存ownerの写像を使う。必須入力自体が未解決なら`Unknown(missing_input)`、読取失敗なら`Unknown(unreadable)`、必要な宣言/readerの未登録なら`Unknown(unregistered)`、まだ読んでいない場合は`Unobserved(not_run)`。L9がreasonを限定していない箇所でreasonを決められない場合は、K1の非肯定classだけを固定しreason選択をL6へ未決で渡す。revision変更は既存K2規則の`Stale`/`Unobserved`、同revision異bytesは`Unknown(conflict)`とする。K5/K6 receiptは読取範囲の証拠であり物理適用や成功そのものではない。

各L9 verifier行は正常baselineのfixture IDと、そこから一条件だけ変えたfixture ID群へ展開する。`L8-INFRA-<parent>-<verifier>-<condition>`は一意IDであり、conditionは下の各行で文字どおり定義する。合成器はfixture間で条件を合成しない。確定したdomain mismatchはその観測値の`Value`であり、K1 `Unknown`へ言い換えない。owner polarityやL9で指定されないreasonは新設せず、上記の理由対応で定まらないものだけ「reason未決」と明記する。

### 2.1 独立fixture ID、K1期待、API対応

`IV-INFRA-006-02`の各`KIND-*-BASE`は、当該kindに結び付く既存owner `OperationDecl`、完全なK3 key、current actor/target/action/revision/environment/scope/expiry、その他required input、permission、policy、credential scopeがすべてbaseline値を持ち、合成K3 checkが`Value(Positive)`となるfixtureである。これは合成入力のbaselineであり、現行owner sourceでbindingが解決できないoperationの実状態を肯定しない。その場合は当該operationだけK3の既存non-positive結果を保ち、未決のclass/reasonを新設しない。各negative rowはこのbaselineの一入力だけを変更する。

INFRA operation `kind`はK3 `PermissionQuery.operation`と別項目であり、K3 actionは既存owner `OperationDecl`のbindingからだけ与える。OS ownerが宣言するoperation/attempt observation refとK7 generation pointer/EpochToken fencing inputを分離する。OS owner refのsource/typeが未宣言・未解決なら該当operationだけ未決とする。fixture IDは各入力組と期待結果を個別に示す。以下で波括弧を使う場合も、展開した各IDを別fixtureとして扱い、1 fixtureにつき1条件・1期待結果とする。各verifierのbaselineは§2.1または§2.2のfixture表に、具体的なID・API・入力・期待結果を明記する。`IV-INFRA-006-02`はkind別に5つのbaselineを定義する。NFR-006-01はその5つのkind baselineを再利用し、NFR専用の重複baselineを定義しない。確定した不一致は既存owner domain value/polarityが定義される場合に限り`Value`へ写す。K1が不在値の具体表現を定めていない場合は値を捏造せず、そのmappingだけ未決として非肯定に保つ。K1 class/reasonがL9で定まらない場合は新しいreasonを選ばず、未決境界を個別に記す。
