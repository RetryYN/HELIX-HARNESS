# HELIXの構造仮説（システム群）

recorded_at: 2026-09-18（Asia/Tokyo）
status: structure_hypothesis_under_verification
authority_effect: none

本書は、HELIXをどのシステム群で構成するかの仮説と、その仮説がどこまで確かめられたかを持つ。
仮説の入力はPOの構想であるが、本書の構造が正しい根拠は「POがそう言った」ことではない。構造の正しさは、
下の「確かめたこと」と、今後の要求形成・設計・検証で示す。確かめられない部分は仮説のまま扱い、固定しない。
発言は要求・仮説・構想であり、逐語に拘束されない。構造を改めるときは、本書を通常の改訂で直す。

本書だけでは恒久authorityや承認を生成しない。承認済みの[Concept v4.1](helix-concept-v4.1.md)と4対象L1を上書きしない。
本書の構造をConceptまたはL1へ反映する場合は、`concept_revision`または`planning_revision`として別に扱う。

用途は、旧要求と現行要求へ「どのシステムの要求か」のラベルを付ける分類軸である。
最初の適用は[旧Requirement IR 153件の分類](../governance/legacy-ir-structure-classification.md)、
旧confirmed identity 175件と現行L2への適用とカバレッジは[要求のカバレッジ](../governance/helix-structure-requirement-coverage.md)である。

## 構造図

T、V、Oは下の図の形を説明する言葉である。分類軸はT、V、Oではなく、下の表のシステム群
（フルリバース、サービス①〜⑦、開発方式の枠、コア、チケット、OSの管理・推進・検収）である。

```
      ╭──────────────── O：循環（HELIX-OSが回す） ─────────────────╮
      │   管理 → 推進（チケット発行）→ 実行 → 検収 → 改善 → 管理 … │
      ▼                                                            │
 ━━━━━━━━━━  T の横棒：ユーザーが受け取る成果物（個別にリリースできる） ━━━━━━━━━━
  ①画面プロト/PoC  ②要件定義  ③設計  ④開発  ⑤リファクタ  ⑥リリース  ⑦運用保守
 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┯━━━
                                 ┃                                     │
   V の左腕（作る）              ┃ T の縦棒 ＝ コア                    │
   ①企画・プロト ╲──────────────╂──────────────╱ ⑦運用・改善 ────────╯
   ②要件定義      ╲─────────────╂─────────────╱  ⑥リリース・受入
   ③設計           ╲────────────╂────────────╱   総合・結合テスト
                    ╲───────────╂───────────╱    単体テスト
                      ╲  ④開発  ┃ ⑤リファクタ   V の右腕（確かめる）
                       ╲────────┻────────╱
                                 ┃
        接続の状態、JSON、Python意味コア、Node/TSテスト、CI機構

   入口：フルリバース ─▶ Vのどの高さからでも入れる
```

| 図の中の形 | 意味 | 入るもの |
|---|---|---|
| Tの横棒 | ユーザーが受け取る成果物。個別にリリースできるサービス | ①画面プロト／PoC、②要件定義、③設計、④開発、⑤リファクタリング、⑥リリース、⑦運用保守 |
| Tの縦棒 | コア。全サービスを横断して成立させる | 接続の状態（trace、依存、stale）、JSON、Python意味コア、Node／TSのテスト、CI機構 |
| Vの線 | 枠。開発方式がサービスを工程として並べる | Vモデル、アジャイル、ハイブリッド。接続要求、V-pair、Gate |
| O | HELIX-OSの循環 | 管理（土台）→推進（チケット発行、レーン、サブエージェント）→検収（CI、テスト、ベンチ）→改善 |
| 入口 | フルリバース | 持ち込まれた要件、コード、PoCをHELIX流へ変換する |
| チケット | 3機構をつなぐ単位 | コアの接続状況から安全な順序を決めて作業を発行する |

### 層で見た概念図

同じ構造を、上から下へ層として並べた図である。上ほどユーザーに近く、下ほど成立させる仕組みである。

```
 ┌────────────────────────────────────────────────────────────────────
 │ HELIX-Web（ユーザーへの窓口）：欲しい成果物を選んで、受け取る
 └─────────────────────────────────┬──────────────────────────────────
                                   │ 成果物
 ┌─────────────────────────────────┴──────────────────────────────────
 │ HELIX-HARNESS ＝ 個別にリリースできるサービスの集合
 │
 │   ①画面プロト   ②要件定義   ③設計     ④開発    ⑤リファクタ  ⑥リリース  ⑦運用保守
 │    ／PoC                                          リング
 │    HTML,PoC     書類        設計書     コード    きれいな      インフラ   ログと
 │                                                  コード                  改善
 │
 │   入口：フルリバース
 │       持ち込まれた既存のもの（要件、コード、PoC）をHELIX流に変換する
 │       どのサービスからでも入れる
 │
 │   枠：開発方式（Vモデル ／ アジャイル ／ ハイブリッド）
 │       サービスを工程として並べる。並べたところに接続要求とGateが生まれる
 │
 │   部品（複数のサービスから使う。仮置き）
 │       要求エンジン、デザインHARNESS、リサーチWorkflow、Design Template
 └─────────────────────────────────┬──────────────────────────────────
                                   │ 全サービスを横断して成立させる
 ┌─────────────────────────────────┴──────────────────────────────────
 │ HELIXコア
 │   接続の状態（要求—設計—実装—テストのtrace、依存、stale）
 │   JSON（意味と正本の形式）、Python意味コア、Node／TSのテスト、CI機構
 │   方式の選択はADR、品質の制約は要求として持つ
 └─────────────────────────────────┬──────────────────────────────────
                                   │ コアを管理し、動かす
 ┌─────────────────────────────────┴──────────────────────────────────
 │ HELIX-OS
 │   管理層（土台）：コアを管理する。登録、分類、revision、証拠、authority
 │      │           省力化の装置：登録bot、監査crawler
 │      ├─▶ 推進機構：コアの接続状況から安全な順序を決め、チケットを発行
 │      │       └ 作業の実行者：エージェントレーン、HELIXサブエージェント
 │      └─▶ 検収機構：チケットから必要なCIとテストを割り出して最適化
 │              └ HELIXベンチ、CI、quarantine、Bugbot
 │   改善loop：⑦運用保守とOSのログ・学習から、HARNESS自身へ改善を戻す（仮置き）
 └────────────────────────────────────────────────────────────────────

   チケット ＝ 3つの機構をつなぐ単位
     管理（接続の状態）→ 推進（発行）→ 実行者 → 検収（検証の集合を決める）→ 管理（結果を記録）
```

サービスは単体要求、枠に並べたときの受け渡しは接続要求、開発全体は構成体要求に対応する。
これは[製品責務境界](product-boundary.md)に記録済みのPO決定（要求をunit、connection、compositeに分ける）と同じ枠組みである。

## 確かめたことと、まだ確かめられていないこと

確かめたこと。

- 旧要求はシステム単位で書かれている。旧IR 153件、旧confirmed identity 175件、現行L2 37件の計365件は、
  21のシステム群codeのいずれかに主の所属を置けた。置き場のない要求は0件である。
- 独立review（GPT-6 Astra、read-only）は365件のうち主の所属の誤りを6件、製品区分の訂正漏れを1件指摘し、
  すべて修正した。区分そのものが成り立たないという指摘は無かった。
- 「HARNESSは規範、OSは登録・版・運転」という境界は、製品区分の訂正案7件と`L2D-S1-01`の分割案で同じ形に現れる。

まだ確かめられていないこと。

- サービス④開発、⑥リリース、⑦運用保守は、旧要求がほぼ無い。区分として要るかどうかは、要求を実際に形成して
  初めて確かめられる。
- 「個別にリリースできる」こと（サービス間が密結合でないこと）は、要求の分類では証明できない。依存関係の設計と、
  単体での受入検証で示す。
- 部品（要求エンジン、デザインHARNESS、Design Template、リサーチWorkflow）を独立の区分にするか、サービスの中身に
  するかは、どちらが単体リリースと再利用に効くかを設計で比べて決める。
- 分類は1人の作業者と1回の独立reviewに基づく。1つの区分で旧要求から現行L2への移し替えを実際に行い、
  区分が作業の単位として機能するかを確かめる。

## DDD設計とTDD開発との関係

- 各サービス、部品、コア、OSの各機構は、DDDの境界づけられたcontextの候補である。接続要求は、contextの間の対応関係に当たる。
  旧要求の`HIL-FR-40`（Domain Object/Naming Catalog）と`HIL-NFR-25`は、この設計規律を既に要求として持っている。
- 各単位が要求・設計・実装・テスト・検証を一式持つことは、TDDで検証を先に閉じることと対応する。
  現行の`HARNESS-L2-003`は、L6↔L7でRed→Green→Refactorを閉じることを既に述べている。
- contextの線引きそのものは設計（L3以降）で決める。本書と分類台帳は、その入力となるラベルを与えるだけである。
