## 内容レベルの回帰確認

### OS

- **正常系**: authorityとsource revisionが依頼scopeに結び付き、限定されたWorker実行がassignment/evidenceを保持し、現行oracleに従って元Workerへ戻せる。初回は、現行の低リスク6条件、authority、明示されたtask制約を満たす場合に限りBench評価なしで開始できる。その結果はLABO証拠がそろうまで未評価のままとする（L2/L11-027、OS-018/019/023、LABO-055/054）。
- **反例**: Bench scoreがassignment/merge authorityを生む、signalが承認済みworkflowを変える、stale attemptが未完了義務を失って再開する、送信receiptをconsumer受領と呼ぶ、変更HEADに旧HEADのreviewを流用する。現行OS L2/L11-001/004/007/009/015/018/019/023/027/029の該当受入条件で失敗または確認対象とする。
- **数値・authority・版**: 旧lane/provider/cycleの固定値は現行要求ではない。budget/timeboxは明示された限定taskと停止条件に従い、この旧sourceから数値defaultを移植しない。OS-027は未評価の性能と既存security authorityを区別し、自分で権限を作らない。OS-014のstage releaseとOS-026のscope導出は別の責務である。OS execution recordだけではHARNESS成果物をVerified/Acceptedにしない。
- **残置**: 内部auditはOS-001〜013をsource routing containerとし、IDごとのcandidate登録ではないと記録する。旧atomごとの後継対応と除外理由は別途未完である。RLO-FR-040/RLO-AC-030だけでは初回割当・実行は閉じず、現行L2/L11-027と既存owner契約が開始入力と実行後結果を接続する。実行・測定済みの合格は主張しない。

### INFRASTRUCTURE

- **正常系**: 現行resource identity/environment/version/provenanceを観測し、desired/actual/driftを区別する。実操作はplan→許可されたWorker apply→before/after/diffを含むreceiptの順で扱い、restore/rollbackは明示された互換targetと証拠がある場合に行う。read-only fixtureでもoperation scope/write-set、write禁止、操作起因の変更なしを観測するが、全runtime digestの不変までは要求しない。OS停止中も独立OOB authorityで復旧を始められ、復旧後にOSへ同期する。
- **反例**: ambiguous/unknown/stale targetをhealthyとする、planをapply済みと報告する、before/after receiptを欠く、read-onlyと宣言しながらwrite制御を観測できない、restore名だけで結果を示さない、旧stateやcandidate generationをrunningと混同する、OS task authorityをINFRAへ移す、AWS固定・multi-region・自動failover全体を一律1.0とする。L2/L11-001〜011/025の適用条件が該当例を扱い、012〜024/026は後続版に残る。
- **数値・authority・版**: POが決めた18項目は現行1.0のaggregateであり（L2/L11-011と001〜010/025の18項目表）、任意の18 backup操作を意味しない。resource測定はsource/revision/unit/time/freshnessに結び付き、unknown/staleをhealthyまたは容量十分としない。backup/restoreは対象義務に応じて適用し、L2-011では18項目全体を確認する。容量・閾値はL3で根拠と検証方法を導出する。未承認の旧L3候補値を固定oracleにしない。
- **残置**: auditでINFRA-012〜024/026は「1.0より後（版は未定）」とされており、1.0受入漏れではなく保持された後続scopeである。stage-review receiptの旧atom数0は候補を導出した記録であり、旧lifecycle atom被覆を証明しない。source比較を越える旧line atom→successor対応は未完として別に残す。

### CONNECT

- **正常系**: connection endpointとsemantic/adapter revisionを識別し、既存read accessの範囲で版を比較する。revisionが変わればstaleとし、現行の互換性結果が出るまで送信を止める。実送信では既存action authority/data-use scopeも別途必要とする。同じoperation/digestのretryだけを適用中contractの範囲で行い、unknown/unreceivedとattempt lineageを保持する。一方を置換したら他方を固定してそのconnectionを再確認し、複合成功は必要な登録edgeすべてが技術的に完了した場合に限る。
- **反例**: 互換性比較から送信許可を推定する、revision変更後も過去成功で送る、同一idempotency keyで異なるdigestを成功扱いする、ACK欠落やpermit期限切れを完了扱いする、connectorが業務成功/承認を書く、別connectionでidentity/contract/scopeが異なるendpoint共有を拒否する、3-fixture構成を製品最低数とする。CONNECT L2/L11-001〜007が区別を保つ。L11-007のmulti-edge fixtureは例であり製品・機構の最低構成数ではない。
- **数値・authority・版**: retry上限とexpiryは適用されるconnection contractに従う。旧runtime/API key/独自version値を普遍化しない。互換性比較は送信permitなしでも可能だがread accessは守る。実送信には有効authority、scope一致、未失効が必要で、unknown/expired/revokedなら送信を開始しない。7候補は登録済みconnectionと適用条件の範囲で1.0対象となる。
- **残置**: CONNECTのderived coverage receiptは`source_atom_count:0`であり、導出済み候補を記録するが旧atomを覆わない。internal auditは指定3資産の意味比較を記録する一方、旧source atom全体の後継receiptまでは示していない。空atomの`no_loss`を被覆と数えない。supersede済みL2-006 kindおよびL11-001 endpoint errorは過去の修正であり、現行欠陥ではない。
