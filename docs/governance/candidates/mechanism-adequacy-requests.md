# HELIX 要求指示書｜既存機構の充足性判定と新機構設計

対象：RetryYN/HELIX-HARNESS
版：v0.2／2026-09-05／要求候補（HELIXWeb対象外）
照合基準：main `ff51260578c22124190964b6cc003612a83c075d`

## 1. 目的

実践ログ・検証証拠と要求／設計を機械照合し、「既存機構の修正・接続・再構成で解決できる問題」と「既存構造に不足する能力の設計が必要な問題」を区別する。その不足を反証可能な設計課題へ変換し、AIによる機構設計から実装・検証・運用還流までを既存HELIX工程へ接続する。候補の大量生成や常時A/B探索ではなく、実績・制約・反例から必要な変更を絞り込む。

## 2. 既存責務への接続

今回の対象は現行HELIX本体と既存の開発・運用証拠に限る。HELIXWeb、その専用UI／API、マルチテナント、利用者データ収集・集約基盤は非対象とし、依存・受入・Release条件に含めない。将来構想を理由に専用基盤・空実装・予約schemaを先行追加しない。HELIXWebへの着手は別要求・別承認で判断し、今回の後続必須義務にも置かない。

着手時のmain・関連branch／PR・要求／要件・実装・テストを再照合し、実装済み／未接続／未検収／候補を分離する。新要求の採用前に既存契約との差分と意味変更を整理し、承認後に対象revisionを正本化する。本書だけをruntime authorityにしない。

主担当はUIL-04（#1248）の意味影響・候補合成とし、UIL-05の効果／副作用評価、UIL-06の既存workflow配車へ接続する。System Synthesis（#1033/#1036/#1039）は既存能力の意味接続と構造案、Learning（#1384/#1035）は経験・適用条件・反例・昇格証拠を担当する。AI監査提案は#1409、観測世代は#1344、測定は既存Bench／bounded probeを再利用する。

新しい発明route、独立DB正本、scheduler、承認／完了ゲート、常駐AIループを増設しない。#1037の全体planner自動変更保留を解除しない。既存ownerとの重複があれば契約を統合し、別名の再実装を避ける。

## 3. 必須要求

### R1：実績と既存能力の照合

qualified findingを起点に、要求・責務・不変条件・設計・実装revision・有効設定・呼出経路・Attempt・CI／Review・運用結果をstable IDで結ぶ。失敗だけでなく、継続的な無駄や性能目標との差も対象とする。生ログやAIの感想を確定findingへ直結しない。

対象機構ごとに、適用条件、観測可能情報、保持状態、操作、保証、既知の限界と証拠を参照する。宣言された能力と実稼働能力を分離し、未実装・未接続・設定不備を能力不存在と扱わない。既存registryから導出し、全機構を別台帳へ手入力させない。

### R2：六つの判定

判定結果を①実装・接続不備、②既存方式の適用で解決、③既存部品の再構成が必要、④新機構の設計が必要、⑤証拠不足、⑥要求・制約の再検討に分ける。

④は、限定した要求・環境・変更範囲・確認済み機構集合について、必要な情報／状態／操作／保証の不足を、再現例・反例・構造上の制約から説明できる場合に限る。「世界中の既存方式では不可能」「世界初」とは認定しない。既存技術の導入・転用で満たせる場合も調べ、独自発明を目的化しない。

失敗回数、再発頻度、検索不一致、AIの修正失敗、時間／予算切れだけでは④にしない。既存方式の組合せも対象内で照合し、調査未完を不在へ変換しない。制約矛盾は⑥、適用・比較条件の不明は⑤へ送る。既存の連続失敗警告は診断開始signalとして扱い、新機構必要判定に流用しない。

### R3：反証可能な不足判定

既存方式ごとに、適用可否、実適用の証拠、期待結果／観測結果、残る未充足条件を区別する。相関やAIの原因仮説を確定因果へ昇格しない。

現行機構では区別できない二事例に異なる処理が必要、許可された操作では必須状態へ到達できない、既存方式の制約下では目標と保証を両立できない等の根拠を示す。形式的に確認できる範囲は機械検証し、未確認部分は仮説として残す。有限の失敗例から全方式の不可能を断定しない。

既存解・反証・新証拠が得られたら判定を撤回／再分類できること。前回判定は改変せず履歴と理由を残す。

### R4：AI設計への引渡し

AIには要求・制約・関連設計・実績差分・照合済み方式・最小反例を束ねて渡す。出力は、不足能力、成立すべき条件、最小の構造変更、既存部品の再利用、検証方法、期待効果、副作用、移行／rollbackを持つ設計候補とする。

候補は状態表現・責務境界・データ構造・制御方式・アルゴリズム等を対象にできるが、既存保証を緩めて改善を装わない。判断基準そのものの変更も別の意味変更として扱う。要求変更はRequirement Re-entry、意味保存の再構成は該当Refactoring、新能力はADD_FEATURE等へ既存契約で接続する。判定・候補生成だけで実装・merge・publishを許可しない。

### R5：証拠契約と低コスト運転

充足性判定receipt（仮称MechanismAdequacyAssessmentV1）は、finding／candidate参照、要求・設計・機構のrevision／digest、対象scope、照合範囲と未調査範囲、方式ごとの適用結果、未充足条件、反例／反証、判定理由、未知事項、期限、検証義務を保持する。既存UniversalImprovementCandidateV1へ参照接続し、scope分類・変更種別・配車先と判定結果を別軸にする。

機械判定とAI仮説を分離する。同一の確定入力・policy・検証済み証拠から同一判定を再生成し、AI利用時はmodel／session／context／出力digestを記録する。AI不在でも観測・既知判定・保留・配車統制は維持する。DBは既存event journalから再構築可能なprojectionに限る。

通常の実行ログ収集・正規化・既知照合では追加LLM呼出しを行わない。AIは未解決差分の分析に限定し、同一入力・policy・証拠で再起動しない。追加probeは判別したい仮説と停止条件を先に定め、時間・資源・費用・回数を制限する。打切りは証拠不足として保存する。比較実験は性能等の残る不確実性に限定し、再試行・却下候補の無限再生成を防ぐ。

### R6：現行HELIX内での運用結果の還流

採用後はbefore／after、品質、費用、副作用、再発を同じ適用条件で測り、予測・実測・欠測を分ける。baseline／candidate／post-mainを混同せず、判定誤りも学習材料として記録する。

経験・判定・反例・適用条件を既存Learning／event journalへ責務付きで還流する。単一環境の成功を一般則へ昇格せず、出所・利用制限を保持する。既存のcross-project検証・承認契約は維持するが、横断学習基盤の新設は要求しない。

## 4. 受入条件

1. 六分類それぞれに独立した正例／反例を用意する。未接続、誤設定、要求矛盾、調査打切り、既存解の検索漏れを新機構必要と誤認しない。
2. 不足根拠のないAI主張を拒否し、既存解の提示で新機構判定を撤回できる。判定保留中も無関係な開発を止めない。
3. wrong HEAD、stale証拠、世代／環境混載、欠落edge、反証破棄、二重event、順序変更を検査し、unknownを成功・不存在へ補完しない。
4. 通常観測の追加LLM呼出し0、重複解析抑止、予算停止、権限越境拒否、DB replayを実測する。
5. #1344等の過去事例を判断時点のrevisionで再生し、後日の正解を入力へ混ぜず分類する。新機構を増やした数ではなく、誤昇格／見逃し、診断費用、手戻り、再発で評価する。
6. 実ログ→不足判定→設計候補→既存workflow→独立レビュー／検証→main read-after→L12効果・再発観測を一巡させる。局所greenやmergeだけで全体完了にしない。HELIXWebや外部利用者の実績を待たず、現行環境で検収する。

## 5. 実装・段階導入

まずL1要求・L3要件・L10受入、owner、依存、既存契約との差分、Requirement IRへの収載を整え、必要な対象revisionの承認を取得する。次に①一領域の読み取り判定、②不足から設計候補・既存配車への接続、③現行HELIX内の運用検証・効果測定・再発監視の順で、原子的PLAN／PRへ分割する。各段階で必要なV-pair、mutation／回帰、独立exact-HEADレビュー、DB replay、read-afterを閉じる。

初期対象はCI性能・観測世代・繰返しRecoveryとし、既存P0是正、CI高速化、Cursor実用接続を本機構の完成待ちにしない。既存Release管理へ配置し、非対象と後続義務を明記して、要求→設計→実装→検証→Release→L12の未所属・実装漏れをなくす。
