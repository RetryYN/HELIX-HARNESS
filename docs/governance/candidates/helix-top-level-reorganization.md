状態: レビュー用提案。対象Issue: #1732（Vision／Concept）、#1769（再編管理）。
提出境界: PO確認用のDraft PRまで。PO指示によりレビュー依頼・Ready化・mergeは行わない。

## 1. 今回固定する判断

HELIXの再出発は、次の三つを基準にする。

1. **Vision／Conceptを保護する**。人が何を実現したいか、HELIXが提供する価値、主権・責任の境界を上位に置く。
2. **要求を整理しなおす**。既存実装の保存を目的にせず、上位概念から必要性、受入条件、優先順位、既存要求との対応を再確認する。
3. **自動走行と管理の基盤を残す**。要求に従った実行、検証、停止・再開、進行管理、証拠追跡を成立させる契約と必要な実体を保持する。

固定対象はこの三つの意味と契約である。全既存ファイル、個別実装、gate数、旧PLAN、Issue数を保存対象にはしない。
一方、要求の削除・延期・統合は意味変更として明示し、古いという理由だけで未達要求を消さない。
このPRで固定するのは再整理案であり、全旧遺産の撤去完了、全要求の再承認、Conceptのruntime昇格は主張しない。

## 3. 要求の再整理

既存要求を先に破棄して空の要求書を作る方法は採らない。上位価値との対応を全件で照合し、既存IDを入口に次の結果へ分ける。

| 結果 | 判断条件 | 必要な記録 |
| --- | --- | --- |
| 継続 | 上位価値に対応し、独立した必要性がある | 元ID、要求本文、受入条件、primary owner、残義務 |
| 統合 | 同じ振る舞いと受入条件を重複して要求している | 元IDすべて、後継ID、意味差分、失われない受入条件 |
| 置換 | 上位価値は必要だが旧方式が新定義と衝突する | 旧新対応、consumer、移行条件、検証と旧方式の撤去条件 |
| 廃止提案 | 上位価値への必要性がなく、移管すべき義務もない | 理由、影響範囲、要求変更の判断記録 |
| 未確定 | 根拠、owner、受入条件、対応が不足する | 不足事項と解決先。自動的に廃止・延期しない |

要求は利用者・対象製品の要求と、HELIXの自動走行・管理要求に分ける。これは正本の二重化ではなく責務分類である。
各要求に元の出典、Vision／Conceptへの対応、現行／候補状態、owner、受入条件、delivery配置、依存先を持たせる。
整理表は既存Requirement IRへの移管入力とし、独立した恒久registryを増やさない。

「機能名が残っている」「テストが存在する」「実装済みと書かれている」だけでは要求充足としない。
canonical L1〜L12の上下関係と正規pairの検証で意味と証拠を照合する。
初回再整理では全件の採否と未確定を可視化し、その後、承認された要求群から順に正本へ戻す。

## 4. 残す自動走行・管理基盤

| 基盤契約 | 必要な振る舞い | 再整理時に保護する検証 |
| --- | --- | --- |
| 受付と要求接続 | 人の指示・観測から対象要求と変更範囲へ接続する | 未承認候補やIssue本文から実行authorityを生成しない |
| 実行統制 | assignment、scope、branch、HEAD、lease、budgetに従って実行する | 未束縛起動、二重writer、期限切れleaseを拒否する |
| 継続と回復 | event・checkpointから中断後も残義務へ戻る | session消失、再実行、stale世代で義務消失・二重commitが起きない |
| 品質保証 | 要求とV-pair、機械検証と独立意味レビューを結合する | 未検査・unknownをgreenにせず、旧系のgreenで新系の失敗を相殺しない |
| 変更統合 | PR、CI、独立review、DB投影を同じ対象revisionへ束縛する | 別HEADのreceipt再使用や表示だけの完了を拒否する |

1. 同一観測時点のIssue集合を保存し、要求・PLAN・PR・依存と結合する。
2. 継続／統合／置換／廃止提案／未確定の理由と後継先を記録する。
3. 旧Issueの未達AC・finding・唯一証拠を後継へ移管し、親子Issueと依存を修正する。
4. 廃止・置換は実装完了と区別し、現行GH-FR-017に従う終端decision PRとclosure receiptで閉じる。
5. PLANとcontinuationの次アクションも整合させ、閉じた旧作業が自動再開しないことを確認する。

## 6. 旧遺産の撤去手順

撤去単位は旧定義とそのconsumerである。旧9-mode、`route_mode`、旧層・pair、旧runtime、重複PLAN／証跡経路について、
文書・schema・DB projection・CLI出力・gate・fixture・CI・templateの参照を一組として調べる。

1. Vision／Conceptと要求の保護対象、対象旧経路、後継先を固定する。
2. 後継の契約と検証を先に成立させ、実行writerを一つに保つ。
3. consumer-zeroと未達義務の移管を確認し、旧経路を削除する。
4. 実体の削除後に件数・digest・allowlistを実測値へ更新する。
5. clean checkoutで参照解決、基盤smoke、replay、独立reviewを確認する。

履歴だけで足りる資料はGitのcommitから復元できることを確認して作業ツリーから外せる。
現行証拠として参照される資料は先に参照と保存先を移管する。履歴の書換え、DBの一括消去は行わない。
CLI／stateの物理改名、配布切替、release／tag／publishは各既存cutover承認契約に従う。
