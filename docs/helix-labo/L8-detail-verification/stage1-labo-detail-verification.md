## 2. Functional fixture一覧と共通基準

L9の28 functional oracle IDは変更しない。L8 fixtureは各oracleの独立した入力variantであり、同一oracle内に複数の単独変異がある場合はこの節の別行にする。各fixtureは表の基準入力から「単一変異」列だけを変える。L9が明示する複合入力だけは、その行で複合条件と記し、単独変異の行と混ぜない。`C04`と`C09`のhistorical参照と旧revision current偽装は同一入力意味なので、下表の共通fixtureを両oracleから参照し二重作成しない。

共通基準 `BASE-001` は、選択済みsource contractの完全なidentity/revision/digest、許可scope/schema/provenance、完全な observation `SubjectRef`、20 fields、source ownerが宣言したsource status、raw record digestを持つ1 sourceと、有効な別sourceを含む。owner declarationにはcurrent refと既知のhistorical refの両方がある。`BASE-001-HISTORICAL`は正確なhistorical `source_ref`とその時点の`input_heads`を選ぶ正常対照である。`BASE-011`は完全なAggregate refs、`selected_connection` API引数、ownerが宣言したcurrent contract/schema/provenance/receipt refsを含む合成入力である。ただし、どの値をK2 keyのsubjectとどの値をinputsへ入れるかは固定L4/L5で決まっていないため、この基準はそのkey projectionを確定したことを示さない。`BASE-011-PRIOR-VALUE`は、各行が明示する場合に限り、K2 `ResultKey`をその全fieldから導出したうえで記録済みのK2 `Value`をfixture前提として置くsetupであり、変異ではない。selected-connection/receipt key placementが未決の行にはこのpriorを当てはめず、Stale/Unobservedを導かない。`EpisodeCandidate` payloadはL5定義の`candidate_ref`、`observation_refs`、`source_refs`、`source_contract_refs`、`schema_refs`、`provenance_refs`、`relation`、`causal_assertion`だけを持ち、`field_presence`、connection、receiptは追加しない。以下のAPI型はL5の既存3 APIに固定する。K2 key形成に必要なAPI引数のSubjectRef欠落がL4で必須key欠落と確定する場合だけ既存K2 `Rejected(missing_key)`を期待し、K1 `Observed`へ包まない。APIに正しく渡されたSourceObservation内のdomain field欠落はK2診断にせず、domainの`Missing`として保持する。K1 classとLABO field/statusを別記録し、L4/L5でそのdomain条件からK1 classへの写像が定義されない箇所は局所未決として値/reasonを作らない。20 field欠落時はL5 §3.1の必須fieldを成功扱いせず、L4の既存`Unknown(missing_input)`分類に基づき、`field_presence=Missing`および`lab_processing=Unknown(missing_input)`を記録する。

`返却候補`/`返却sequence`のfieldを変えるvariantは、関数入力を変えた製品API試験ではなく、L9 oracle comparatorへ誤ったprojectionを与えて検出可能性を確かめる自己検査である。SUTの実戻りclassは別に記録し、この自己検査からK1 classを生成しない。出力自己検査は、source/status/schemaの製品API入力を一つだけ変えるvariantとは区別する。
