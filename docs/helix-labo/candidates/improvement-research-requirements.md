# HELIX-LABOの改善研究・技術調査・横断診断・学習の要求候補

## これは何か

HELIX-OSの要求案にあった項目のうち、担当がHELIX-LABO（全体の改善研究機構）である項目を、2026-09-25のPO判断によりここへ移した。
移した文言は元のまま保持する。HELIX-LABOの企画（L1）は、[L1企画案](../L1-planning/labo-intent.md)がPOによる対象revisionの確認待ちである。そのため本書は要求（L2）ではなく候補であり、
L1企画案のrevisionをPOが確認した後に要求として採否する。本書から要求の採用・承認・実装許可を生成しない。

元のIDは、追跡のためにそのまま使う。HELIX-OSの要求案には、同じIDの行を移管先の案内として残す。

## 学習に関する候補条件（RCLS）

出典は[RCLS](../../../archive/legacy-generation-2026-09-14/root/docs/governance/candidates/responsibility-centric-learning-requests.md)である。

| 出典 | 保持する具体条件 |
|---|---|
| RCLS-BR-001 | 知識・経験の所有を安定したresponsibility_idで追跡し、フォルダやSkill名の変更で失わない |
| RCLS-BR-002 | CASE／SCENE／PATTERN／LOG／VERIFYを責務・事例・revisionへ対応づけ、相関を因果、自己評価を独立検証として扱わない |
| RCLS-BR-003 | 割当には責務・事例・リスク・provider・task class・context budgetに応じた最小packetを使い、全記録を一括投入しない |
| RCLS-BR-004 | project内、独立検証、横断検証、shadow、Mechanismへの段階を区別し、機構化した規則のSkill本文との二重管理を解消する |
| RCLS-BR-005 | 反例・authority変更・provider／model／version・期限・security／licenseを適格性へ反映し、失効・矛盾・取消後の再検証を確認できる |
| RCLS-BR-006 | 学習結果は提案・証拠・検索入力として扱い、要求・設計・merge・Release authorityを直接書き換えない。既存の要求形成・改善機構を重複実装しない |

RCLSの最小packetはsceneとartifact classも保持して決定的に構成する。学習の仕組みを既存の要求形成・改善・評価機構と重複実装しない。

## L11受入候補

全件未実行である。

| 元のID | 受入条件 |
|---|---|
| HELIXOS-L2-012 | 内部情報の欠落と外部情報の相違を保持し、秘密送信、取得命令実行、外部patch自動採用、closed／mergedだけの解決認定を拒否する |
| HELIXOS-L2-013 | 同じ仕事について上流からの欠落と失敗からの原因候補を突合し、管理自身を含む是正ticket、再検証、再観測へ辿る。未着手や観測停止を正常と表示しない |

RCLSは採用revision確定後に次を確認する。

- 責務名や保存場所の変更後も経験の所有を追跡できる。事例・推論・検証を区別し、自己評価を独立検証として表示しない。
- 割当packetの選択根拠と予算を確認し、全Skill・memory・logの一括投入を認めない。昇格段階と失効・取消後の再検証を識別できる。
- 学習提案だけで要求・設計・merge・Releaseが変更されない。機構化後の規則がSkill本文と二重に判定を支配しない。

## HELIX-Web由来の実績に対する追加候補（2026-09-26）

2026-09-26にPOが示した「HELIX-Web製品群 要求原案」の14節は、LABOに内蔵するHELIX-Benchへの追加を求める。原案は、独立した`helix-web-bench/`を作らず本書へ接続・追記するとしている。
以下に、原文のID・種類・文言のまま載せる。出典は[原文のsnapshot](../../../helix-web/docs/helix-web/sources/helix-web-product-group-requirements-po-original-2026-09-26.md)の325〜351行であり、見出しの階層だけを一段下げた。
原文の状態は「要求候補・未採択」である。本節は上の移した要求と同じく候補であり、要求の採用・承認・実装許可を生成しない（[判断記録](../../governance/decisions/helix-web-product-group-po-decisions-2026-09-26.md)）。
HELIX-Benchは、Conceptの機構の表のとおりLABOの中にあり、LABOと並ぶ機構にしない。

### 14．HELIX-LABO内のHELIX-Benchに対する追加要求

**目的：Web由来の実績を用いて、HELIXによる性能差吸収と改善効果を評価し、公開統計・配置・予測・本体改善へ返すこと。**

所属：`HELIX-LABO`  
ID接頭辞：`HELIXLABO-L2-WEB-`

現行LABOの観測集積、episode化、比較実験、Feedback、変更後の再観測へ接続する。BenchをLABOと並列の機構やWeb専用の別評価エンジンとして新設しない。

| 番号・種類 | 要求 | 受入候補 |
|---|---|---|
| **001・接続** | Web由来の要求、構造、ticket、Worker、モデル、実装、レビュー、CI、リリース、稼働、障害、復旧をepisodeとして関連づけること。 | 成功だけでなく失敗、拒否、取消、保留、不明、未観測を保持する。 |
| **002・接続** | 作業種別・難度・案件特性、HELIX版、モデル・effort・編成、エディタ・拡張・OS・実行資源を比較条件として記録すること。 | 実際に取得した情報、利用者登録情報、推定、不明を区別し、実モデル名等を憶測で埋めない。 |
| **003・単体** | 同じ受入基準への到達率、品質のばらつき、時間、費用、再作業、介入量から性能差吸収を評価すること。 | 品質水準を下げて差を縮めた結果を改善とせず、到達品質と必要資源の両方を示す。 |
| **004・単体** | HELIX有無、機能有無、旧新版、編成・effort等の比較を、通常利用の観測と条件を揃えた実験に分けること。 | 案件難度や割当傾向が異なる単純平均から因果効果を断定しない。 |
| **005・単体** | 実作業、待機、レビュー、再試行、救援、人間介入を含む完了時間と総費用を計測すること。 | 上位モデルの救援を隠さず、並列時間を単純合算して経過時間と混同しない。費用の実額・配賦・推定を区別する。 |
| **006・単体** | 初回受入率、最終受入率、見逃し、再作業、運用後の障害・復旧・再発を、観測期間付きで評価すること。 | 新しい成果物の「まだ障害がない」と、長期安定実績を同じ品質として扱わない。 |
| **007・単体** | 非同期バッチで日次集計し、重複、遅着、訂正、欠測、再集計を扱うこと。 | 同じ入力集合・評価版の結果を追跡でき、訂正時に集計履歴と理由を残す。 |
| **008・接続** | 公開用結果に母数、案件数、期間、条件、評価方法、除外理由、ばらつき・不確実性、集計版を含めること。 | 少数事例を一般化せず、成功例だけを抽出した統計を全体実績として公開しない。 |
| **009・単体** | プロバイダー・モデル・effort・エディタ・環境別の残差を調べ、HELIXが吸収できていない条件を特定できること。 | モデル順位を結論にせず、要求形成・工程・実行環境・検証等の改善候補へ分解できる。 |
| **010・接続** | 品質を満たすモデルクラス・effort・編成、予測時間、必要な救援条件をINTELLIGENCEへ渡すこと。 | 適用範囲と根拠が付き、過去の集計だけで未知の案件への成功を保証しない。 |
| **011・構成体** | 運用保守の成功・失敗・復旧・再発を比較し、条件付きのパターン・反例・限界を抽出すること。 | エラーログの羅列にせず、要求・設計・変更・環境・対処結果との関係を保持する。 |
| **012・接続** | 顧客固有の意味と汎用化できる構造を分け、評価済みの候補をBRAINまたは製品COREへ返すこと。 | 顧客名、秘密情報、固有業務ルール、単発の修正を共通知識へ直接昇格させない。 |
| **013・構成体** | 改善候補を対象機構へ返し、採否、変更、検証、リリース、Web適用、再観測まで追跡すること。 | Feedbackを返しただけで改善完了とせず、新版の効果・退行を確認する。 |
| **014・構成体** | 比較実験の対象、予算、データ、実行場所を案件運転から分離すること。 | 公開統計のために顧客の作業を無断で複製実行したり、利用枠を消費したりしない。 |

公開値は**HELIX利用者・登録案件の実績**として扱い、市場全体のシェア・性能分布へ読み替えない。
