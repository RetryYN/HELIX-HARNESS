### F01 — single-runtimeレビューの未記入・未知status・重複IDが拒否されない（P0）

**根拠:** [src/gate/review-tier.ts](https://github.com/RetryYN/HELIX-HARNESS/blob/b5178c34fe34c956a70713ad942b1f5b8f64e0ab/src/gate/review-tier.ts)、[src/gate/review-tier-policy.ts](https://github.com/RetryYN/HELIX-HARNESS/blob/b5178c34fe34c956a70713ad942b1f5b8f64e0ab/src/gate/review-tier-policy.ts)。抽出した判定ロジックで反例確認。

**成立条件:** 単一runtimeのjudgment reviewで、必須7 IDを含むchecklistを渡す。

**確認結果:** DOC/TST/COD/XR/DEP/DUP/MODを全て置きstatusを省略するとmessages=[]。PASS/skipも同じ。DOCのfailの後に同ID passを追加するとMapが後勝ちになりfailを消す。

**影響:** レビュー未確認を確認済みとして扱うローカルゲートになる。旧単一runtime経路を新Ticket等が再利用すると弱さを引き継ぐ。

**是正方針:** 入口でstrict schemaとID exact set/重複禁止を検証し、未知値は明示拒否する。intra-runtime補助検査を独立reviewの代替へ昇格しない。

**受入oracle:** 必須7 ID全てstatusなし / PASS/skip/unknown / fail→同ID pass / 正常pass、fail、根拠付きN/Aの対照。

**既存追跡:** [#1411](https://github.com/RetryYN/HELIX-HARNESS/issues/1411)。既存Issueの現行コード再確認。重複IDの具体例も記録。

**未証明・注意:** プロジェクト全体のmerge通過は未実証。#1411本文の単一ID例はこの実装ではmissingを発生させるため、全必須IDを揃える反例に補正した。

**同梱反例:** `REVIEW-missing, REVIEW-PASS, REVIEW-skip, REVIEW-duplicate`。

### F02 — 検証manifestが実証拠と必須集合を独立に確認していない（P0）

**根拠:** [src/lint/gn-evidence-manifest.ts](https://github.com/RetryYN/HELIX-HARNESS/blob/b5178c34fe34c956a70713ad942b1f5b8f64e0ab/src/lint/gn-evidence-manifest.ts)。抽出した判定ロジックで反例確認。

**成立条件:** validateGateEvidenceManifestへ構造の整ったmanifestと存在する合成ファイルを渡す。

**確認結果:** 実内容と無関係な全ゼロsha256でも違反0。mandatory_item_idsとcoverageを空にすると個別検査が消える。パスhelperは外部を指すsymlinkやdirectoryも存在として受理する。

**影響:** 証拠が実行結果を裏付けなくてもvalidator単体は成功し、要求した検査対象の脱落を見逃す。

**是正方針:** 必須集合をauthoritative test design/verification planから導出してexact比較する。digestが何のバイト列を表すかを型で分け、実行receiptの発行元・HEAD・対象・結果へ照合する。file evidenceにはrealpath/regular-file境界を検討する。

**受入oracle:** 正常証跡に対するwrong digest / 必要義務があるのにmandatory=[] / 偽のpassed/exit criteria / 外部symlink・directory・missing file。

**既存追跡:** [#1430](https://github.com/RetryYN/HELIX-HARNESS/issues/1430) / [#145](https://github.com/RetryYN/HELIX-HARNESS/issues/145)。既存#1430を対象関数で再確認。パス実体境界も補足。

**未証明・注意:** output_digestを安易にテストソースファイルのhashへ変更しない。実行stdoutとファイル証跡は別物であり、その契約の確定が先。全G8/G9/G10やCI一式の迂回は未実証。

**同梱反例:** `EVIDENCE-bogus-digest, EVIDENCE-empty-required, EVIDENCE-symlink, EVIDENCE-directory`。

**影響:** 自然な説明の追記やplaceholderで承認検査の適用・入力品質が弱まる。

**是正方針:** operation/target/environment等のtyped属性と既存brokerで承認要否を判定する。自然文は補助情報に限定。承認fieldのschemaと参照receipt実在・scope/expiry/actor bindingを共通化する。

**受入oracle:** 同じ実行内容に証跡/説明/サンプルを加えても適用が消えない / 4 placeholderが未確定 / scope/HEAD/expiry/actor不一致。

**既存追跡:** [#1431](https://github.com/RetryYN/HELIX-HARNESS/issues/1431)。既存#1431の現行再確認。

**未証明・注意:** 周辺のbrokerや他の承認ゲートを越えて危険操作できるとは実証していない。field判定と適用分類の欠陥である。

**同梱反例:** `APPROVAL-evidence-word, APPROVAL-placeholder-TBD, APPROVAL-placeholder-pending, APPROVAL-placeholder-N/A, APPROVAL-placeholder--`。

### F04 — 旧loopのverdictが引用中のpassを最終failより優先する（P1）

**根拠:** [src/orchestration/loop-bridge.ts](https://github.com/RetryYN/HELIX-HARNESS/blob/b5178c34fe34c956a70713ad942b1f5b8f64e0ab/src/orchestration/loop-bridge.ts)。抽出した判定ロジックで反例確認。

**成立条件:** exit 0のverifier出力に引用・例示と最終結論が混在する。

**確認結果:** Example: VERDICT: pass→最終行VERDICT: failでもpass。JSON verdict=failとstderr診断の組合せはJSON解析に失敗してpendingとなる。nodeTickDeps.runVerifierから呼ばれる。

**影響:** 旧loopの判断が誤り、修正継続/検収状態を取り違える。

**是正方針:** 自由文からのfirst-matchを廃止し、専用のstrict terminal envelopeを唯一の入力にする。stdoutの機械結果とstderrのログを分離し、曖昧・複数・欠落はinvalid。

**受入oracle:** 引用pass＋最終fail / 複数verdict / JSON＋stderr / exit非0＋pass / verdict欠落。

**既存追跡:** [#1416](https://github.com/RetryYN/HELIX-HARNESS/issues/1416)。既存#1416の再確認とJSON/stderrの追加例。

**未証明・注意:** 現在の新resident全体がこの経路を使うとは主張しない。旧engineが残存する間の局所欠陥。

**同梱反例:** `VERDICT-quoted-pass, VERDICT-json-stderr`。

### F05 — READY投影が過去の合格を現在の根拠にできる（P1）

**根拠:** [src/workflow/readiness.ts](https://github.com/RetryYN/HELIX-HARNESS/blob/b5178c34fe34c956a70713ad942b1f5b8f64e0ab/src/workflow/readiness.ts)。SQL/分岐の合成再現。

**成立条件:** 同じPLANに古いpassed gateと新しいfailed gateがあり、open finding/human blockがない。

**確認結果:** passedGateCountはPLANとstatus=passedだけを数え、1件あればreadyとなる。HEAD/phase/必要集合/最新状態を見ない。subject_id LIKE %PLAN-1%はPLAN-10のfindingも拾う。

**影響:** READY表示・投影を実配車判断に利用する場合、古い合格による過剰許可や無関係findingによる停止を起こす。

**是正方針:** 対象run/PLAN revision/HEAD/phase/required gate exact setへjoinし、現在有効な証拠からREADYを導出する。subjectの関係はexplicit keyか正規関係tableで解決する。

**受入oracle:** 旧HEAD pass＋現HEAD fail / required gate不足 / PLAN-1とPLAN-10 / query error/missing input。

**既存追跡:** [#1442](https://github.com/RetryYN/HELIX-HARNESS/issues/1442)。LIKEは既存#1442。古いpassの再利用は今回具体化した追加論点。

**未証明・注意:** 原TypeScriptモジュールではなくliteral SQLと分岐をインメモリSQLiteで再現。現行CLI/配車までの全到達性は未完了。例外がreadyへ握りつぶされるとは確認していない。

**同梱反例:** `READY-old-pass-new-fail, READY-prefix-overmatch`。

### F06 — DBパスの検査基準と実際に開く基準が異なる（P1）

**根拠:** [src/state-db/index.ts](https://github.com/RetryYN/HELIX-HARNESS/blob/b5178c34fe34c956a70713ad942b1f5b8f64e0ab/src/state-db/index.ts)。抽出adapter＋実SQLiteで再現。

**成立条件:** cwdとoptions.repoRootが異なり、pathとして.helix/probe.db等の相対パスを渡す。

**確認結果:** assertWithinHelixStateDirとmkdirはrepoRoot基準。一方openNative(path)は未正規化のpathをSQLiteに渡す。抽出adapterと実node:sqliteで、指定repo側にDBはなくcwd側にDBができることを確認。

**影響:** 複数project/worktreeでガードした場所とI/O対象がずれ、誤った状態の読取・作成・更新につながる。

**是正方針:** pathを一度だけrepoRootから絶対化し、同一値でguard/mkdir/open/返却を行う。または異なるrepoRootでの相対pathを明示拒否する。read-only側も同じ規約に揃える。

**受入oracle:** cwd=A/repoRoot=B/relative path / absolute pathの対照 / cwd非依存のread-only / symlink/reparse/drive境界。

**既存追跡:** [#1397](https://github.com/RetryYN/HELIX-HARNESS/issues/1397) / [#1218](https://github.com/RetryYN/HELIX-HARNESS/issues/1218)。今回追加で具体化。openNativeおよびrepoRoot/cwdのIssue検索では同一原因の専用Issueを確認できなかったが、未登録の断定はしない。

**未証明・注意:** この入力を全既存callerが使用しているという主張ではない。実際の作成先違いは合成環境の公開adapter入口で確認した。

**同梱反例:** `DB-relative-root-mismatch`。

**未証明・注意:** 当該関数が受理することを実証したもの。全CI/独立reviewで受理されるとは主張しない。marker数が実consumer数でない点は作者も認識済みで、新規発見として水増ししない。

## 5. 修正の接続方針

### 5.1 既存ownerで修復する

まずF01–F03を既存#1411/#1430/#1431へ結び付け、意味の変わらない局所修復と反例を一緒に閉じる。F06のDB root不一致は既存path/DB ownerへ照会して原子scopeに割り当てる。F07は#1533のマージ前レビュー項目として扱う。これらの修正を理由に新しい巨大planner・別DB・別queue・別harnessを増設しない。

F05のREADYは実consumer到達性を確定してから配車判定への影響を分類する。実際のcurrent routeではないならcompatibility-onlyとして明示し、新しいTicketが再利用しない境界を先に確立する。旧slotのような近似統計をそのままhard capacityへ昇格しない。

### 5.2 安全境界を弱めない

未知statusの受理、必須検証集合の削除、独立reviewの省略、worker-blind provenanceの重複許可、no_harnessを理由にした本線guardの無効化、baselineの上方書換えでCIを緑にしない。正規のinput producerとvalidatorを同じ契約へ接続する。

### 5.3 機械で検収する証拠

各修正は、対象HEAD・対象責務・source revision・test・独立review・CI・DB/replayを同一scopeへ束縛する。修正前にはnegative fixtureが安全要件に対して失敗し、修正後に安全側の期待値へ変わることを、元のTypeScriptモジュールを使うテストで検収する。同梱の局所反例だけを全回帰完了receiptへ昇格しない。

具体的な着手順・並列数は既存dependency/WIP/priority policyが決める。本報告は新しい実行authorityや恒久的なPO指示ではない。
