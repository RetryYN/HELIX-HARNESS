# HELIX VISION
## 世代を超えて、作り、学び、育て続ける。

**ビジョン文書 v0.1｜2026年9月6日｜基礎資料：アーキテクチャカタログ v0.6**

> 一緒に何を作るかを決める。決まったら、検証できるシステムとして届ける。  
> そして、使う人自身が、そのシステムを保守し、改修し、育て続けられるようにする。

本書は、ここまでの対話で示されたHELIXの方向性を整理した長期ビジョンです。将来の能力と事業展開を扱い、現在の実装完了、正式な要件承認、公開版、提供日を認定するものではありません。既存カタログv0.6を上書きせず、その上に未来の物語を置きます。

記述を三つに分けます。**方向性**はユーザーが示した構想、**実現・到達確認案**はそれを成立させるための本書の整理、**未決定**は今後の実証・選択が必要な事項です。発言の根拠は付録U、既存文書の根拠は付録Bで追跡できます。

<a id="vision"></a>
## 1. 原点と到達したい世界

HELIXの原点は、「いいシステムは世代を超えていく」という考えです。一度作って終わるのではなく、開発した成果、失敗から得た経験、検証された改善を、次の仕事と次の世代へ渡していく。生物を模した名前や比喩は、この継承の思想に由来します。[U01][U25]

HELIXが目指すのは、AIに大量のコードを書かせることだけではありません。何を作るかを人間と収束させ、作る方法を組み立て、品質と安全を確かめ、運用へ渡し、その後の変化にも対応できる開発システムです。

中心に置く価値は、**ソフトウェアの所有者が、自分のシステムを自分で育て続けられること**です。新規開発の速さだけでなく、保守・修復・機能改修を利用者の手へ戻すことを目指します。ただし、それをどの版でどこまで実現するかは、操作と対象範囲ごとの実証で判断します。[U17]

事業はHELIX-Web一つで完結しません。HELIXを作り、HELIXを使ってサービスを作り、その実践でHELIXを磨く。HELIX-MARKETINGなどの別事業も並行して育つ世界を構想します。[U18][U19]

<a id="structure"></a>
## 2. HELIX本体とHELIX-FACTORY

### 2.1 本体は「開発する力」と「自分を育てる力」を持つ

HELIX本体では、全体統制の下に開発統制と成長統制を置きます。全体統制は、両者の責務・関係・変更を統括する構想です。個別の要求、実行、品質、安全、公開の権限を、一つの万能な書込主体へ吸収する意味ではありません。[U02][U03][B03]

```text
HELIX本体
└─ 全体統制
   ├─ 共通基盤
   │  └─ 識別・正本／権限・証拠・履歴・契約・実行接続
   ├─ 開発統制
   │  └─ 対象システムを作り、確かめ、届け、維持・改修する
   └─ 成長統制
      └─ HELIXを観測し、経験を継承し、改善・知能化を進める
```

成長側が改修を必要とした場合も、変更は正規の開発経路へ戻します。稼働中のHELIXと改修候補のHELIXを区別し、改善を提案した主体が自分の変更を独立検収したことにはしません。[B03]

### 2.2 FACTORYは、本体を使って事業を生み出す側

**HELIX-FACTORY**は、HELIX本体以外のサービス・事業展開をまとめて捉える名称です。現段階では事業構想上の傘であり、単一の新しい巨大システム、必須共通DB、法人構造やリポジトリ構成を確定するものではありません。[U18][U19]

```text
HELIX本体 ── 開発能力・検収済み成果 ──→ HELIX-FACTORY
                                          ├─ HELIX-Web
                                          │  └─ AI開発SaaS
                                          ├─ HELIX-MARKETING
                                          │  └─ 市場・顧客・利用を扱う事業
                                          └─ その他の製品・アプリ・サービス

HELIX本体 ←── 利用を許可された実践証拠・改善候補 ──┘
```

HELIXは作るための資産を蓄積し、FACTORYは届けるための資産を蓄積します。認証・テナント・課金・サービス運用などを再利用する余地はありますが、これは**実現案**です。使う場面が確認できたものから共通化し、最初から全事業用の基盤を作ることは求めません。

また、「HELIXで開発された製品」と「稼働時にもHELIXを利用するサービス」は別です。全成果物にHELIX本体やConnectorを常駐させる前提にはしません。

### 2.3 二つの「工場」を混同しない

v0.6の内部公開工場は、HELIX自身のPackageを制作・検収・公開する内部工程です。HELIX-FACTORYは、それより広い事業・サービス展開の構想です。名前が似ていても同一責務にはしません。[B02]

外部へ切り出す基本単位は、**利用者が一つの開発責務を実行し、利用可能な成果を受け取れる道具一式**です。必要な基盤も、その開発責務に使う最小範囲へ限定します。HELIX自身の全体統治・学習・機構創出・自己公開工程を丸ごと同梱する構想には戻しません。[U04][B01][B02]

### 3.1 v0.6で整理した出発点

以下は既存資料にある13のPackage候補です。13製品が公開済みという意味でも、最終的な個数を固定する意味でもありません。[B01]

### 3.2 Packageの説明と、所有・配布構成は別

Packageは利用者視点の提供単位、Moduleは既存責務・pathの所有、Functional Release Sliceは検証・昇格・更新／rollbackの単位です。Bundle／Profileは選択された構成、Artifactは実際に渡すbytesとmanifestです。これを一本の包含木へ潰しません。[B02]

本書の**Release Pack**は、必要な開発能力と最小依存を選び、版・内容・検収証拠を束縛して渡す配布物の呼称です。既存Bundle／Profile／Artifactと同じ実体なら、それらを再利用します。新しい恒久的な管理階層を足すこと自体は目的ではありません。

```text
利用者の開発目的
  → 必要なPackageを選択
  → 所有Module内のSliceと必要基盤へ展開
  → 依存・除外・互換性を確定
  → Release Packとして検収
  → ローカル導入／Connector経由の導入・更新
```

この切り出しが、HELIX-Webを接続型サービスとして成立させる布石になります。利用者がCIだけ使いたい場合に、HELIX全体の成長機構まで導入させないためです。[U09]

**配布する道具、道具を使って作る製品、将来提供する学習済みモデルは、異なる成果物です。** モデルのサービス提供を始めても、内部の全学習履歴や全体統制を開発Packageへ混ぜる理由にはなりません。

## 4. 三つの成長軸と、並行する事業展開

未来は三軸で読みます。①本体が何をできるようになるか、②それをどのようなサービスとして届けるか、③利用者自身が何をできるようになるか。HELIX-FACTORYは、三軸を使って別の商品・収益経路が並行して生まれる事業展開の軸です。

**1.0以降は、本体を完成させてからWebを順番に作る一本線ではありません。本体とWebが別々に進み、能力の受渡しで何度も交差します。**[U07][U10][U11]

| 本体のビジョン節目 | ① HELIX本体 | ② HELIX-Web／サービス | ③ 利用者の自立度 |
|---|---|---|---|
| 1.0 | 現在構想の最初の完成。開発・検証・提供・運用を定義した範囲で成立させる | 別進行を始めるための開発基盤・Release Pack | 定型保守を利用者へ開くための基礎 |
| 1.x | 実案件でPackageと並行開発を磨く | Connector型AI開発SaaS。自分の環境をWebから操作 | 限定された更新・診断・復旧から開放する候補 |
| 2.0 | 外部開発データを分解し、現在の案件へ推薦 | 根拠付きの技術・設計・改修推薦を提供 | 影響と選択肢を見て変更を判断する支援 |
| 2.x〜2.5 | 外部知識と実践・開発能力の接続を成熟 | 接続型AI開発SaaSの提供体験を磨く目標帯 | 案内付き改修を拡張する候補 |
| 3.0 | HELIXデータでLLMを学習・チューニング・評価 | HELIX-Web 3：HDAによる分散LLM開発補助 | 専門AIと保守・改修を進める |
| 4.0 | HELIX Intelligenceが開発方法とフローを動的構築 | 目的・計画・根拠・進行をWebから扱う | 要望から改修手順を組ませ、実行を委任する |
| 5.0 | 共同要件定義から検証済みシステムを納品するSystem Compiler | 共同定義・プレビュー・コンパイル・検収・配備の体験 | 要求を変更し、既存システムを差分再生成して育てる |

①2.0〜5.0、②初期Connector型とWeb3のHDAはユーザーが示した方向です。1.0は会話で置いた「現在構想の最初の完成」という作業上の節目で、対象要求の確定は別途必要です。**③の具体的な到達版は提案であり、特に「2.5なら非エンジニアが何でも改修できる」とは約束しません。**[U05][U06][U12][U14][U15][U17]

ここでの1.0〜5.0は**能力進化を説明するビジョン上の節目**です。公開するソフトウェアの互換性に基づく版番号や、既存のG1〜G5という成長評価と自動的に一致させません。[B02]

## 5. HELIX本体の進化物語

### 5.1 HELIX 1.0 — 開発を成立させる最初の個体

1.0では、現在構想の開発能力を、単なる部品の存在ではなく仕事の接続として成立させます。要求から設計・実装・検証・統合・リリースへ進み、配備・運用・保守・診断から適切な変更地点へ戻れることを目指します。HELIX自身への改善も、その開発経路を使います。

**到達確認案：** 1.0に含める要求と利用範囲を先に固定し、代表的な開発・回復・更新で、成果と証拠の受渡しを実証する。選択したPackageについて、必要依存だけで利用・更新・撤去できることを確認する。部品のmergeや文書の存在だけを完成としない。[B01][B03]

1.0完成待ちを利用して、将来構想を際限なくその分母へ足しません。Webサービス、外部データ推薦、モデル学習、知能化、System Compilerは後続のビジョンとして分離します。Connectorサービスそのものの完成を、遡って1.0の必須条件にはしません。[U22]

### 5.2 HELIX 2.0 — 世界の開発経験を現在の案件へ翻訳する

自分の経験だけでなく、OSS、設計資料、Issue、PR、技術文書、研究などの開発データを読み、責務・挙動・失敗・修正・検証へ分解して、HELIXや対象プロジェクトの状態と照合する構想です。[U05]

```text
外部情報の取得・出典保全
  → 開発上の意味単位へ分解
  → 内部の要求・責務・環境との対応付け
  → 適用可能性／不一致／不足根拠を評価
  → 根拠付きRecommendation
  → 必要な調査・限定検証
  → 採用する場合だけ正規の変更経路へ
```

目指す成果は「人気の技術一覧」ではなく、「今回の制約で採用する理由、採用しない理由、代替案、確認すべき条件」です。既存の調査・意味graph・学習機構を再利用し、新しい万能engineを並立させることは前提にしません。

**到達確認案：** 推薦から元の出典・版・根拠へ戻れる。適用不能や判断保留も返せる。推薦の採否と導入後の結果を追え、外部事例の成功を自分の環境の成功へ置き換えない。

### 5.3 HELIX 3.0 — 経験をモデル能力へ定着させる

3.0の明示的な到達点は、HELIXの開発データを、ローカルLLMの学習・チューニングに利用できることです。その先の4.0へ向けたモデル構想は、小型のローカルモデル群だけでなく、Kimi級の大規模な公開モデルの用途別チューニングまで含みます。**ゼロから汎用基盤モデルを事前学習する計画ではありません。** 具体的なモデル・公開条件・利用ライセンス・規模は未選定です。[U06][U13]

```text
利用が許可された開発episode
  → 出典・権利・機密性・結果の確認
  → 学習候補／評価用データの分離
  → datasetと学習設定の版固定
  → チューニング
  → 独立評価・反例・既存能力の劣化確認
  → 限定利用・採用／不採用
  → 実作業の結果を次の評価へ
```

学習方法として、教師あり調整、選好学習、adapter／LoRA、利用条件を満たす蒸留などを比較する余地はあります。ただし手法の採用、学習費用、性能改善は未確定です。責務別モデルを何種類作るかも固定しません。

**到達確認案：** どのデータと設定から生まれたモデルかを追跡できる。学習前との比較、弱点、適用範囲、撤回先を持つ。学習に使った正解や非公開テストを、独立評価の成功証拠として再利用しない。

### 5.4 HELIX 4.0 — HELIX Intelligence

チューニングしたモデル群を、HELIX自身の判断能力へ組み込む段階です。目的、現在のシステム、制約、不確実性、経験、利用可能な能力を読み、その案件に必要な**開発フローそのものを構築し、途中結果に応じて再計画する**ことを目指します。[U12][U13]

```text
目的・現状・制約・経験
  → 必要な責務を推論
  → Capability／Package・モデル・資源を選択
  → 作業、依存、検証義務、人間判断点を構成
  → 既存の権限・品質・安全・実行契約で適格性を確認
  → 実行・観測
  → 残りの仕事を再計画
```

違いは、単にDAGを生成できることではありません。既存の計画・配車・部分合成を土台に、HELIXデータで調整した知能が状況を解釈して開発方法を構成することです。既存の動的な仕組みが4.0以前に存在しない、という線引きにはしません。

大規模公開モデルと小型専門モデルの組合せ、外部プロバイダーへの高難度作業の委譲などは実現案です。自前チューニングを中心方針に置きますが、外部モデルの利用を禁止したり、特定のモデル構成しか成立しないと断定したりしません。

**到達確認案：** 未知の案件でも、必要義務を落とさない実行計画を作れる。計画の根拠・制約・停止条件を説明できる。再計画で以前の承認や検証を勝手に流用しない。推論が誤っても、権限・必須品質・安全の検査で実行を制限できる。

### 5.5 HELIX 5.0 — システムのコンパイル（System Compiler）

人間とHELIXが要件定義まで一緒に行い、確定後はシステム一式の納品を引き受ける段階です。利用者が実装工程を逐一操作するのではなく、確認可能な仕様を渡し、完成条件に照らして検収する体験を目指します。[U15]

```text
人間とHELIXの共同作業
目的 → 調査 → 画面・動作の試作 → 意味・条件・受入の確定
                              ↓
                     確定した仕様revision
                              ↓
HELIXのコンパイルジョブ
設計 → 動的開発 → 品質・安全検証 → 成果物確定 → 納品
                              ↓
                    別途許可された環境適用
```

画面と期待する動きを一緒に作ることを、強い要求入力にします。そこから必要なデータ、処理、権限、状態、外部接続、検証を推論して展開する。画面だけで一意に決まらない目的・制約・費用・データの扱いなどは、必要な部分を確認します。APIやバッチなど画面のない対象では、入出力・動作シナリオを同じ役割の入口にできます。[U16]

**納品物の範囲案：** ソース、実行artifact、確定仕様と設計、検証一式と証拠、出典・供給元情報、環境定義、データ移行、配備・更新・rollback手順、運用手順、検収条件。対象に不要なものを一律必須にせず、納品契約で範囲を決めます。

ここで「コンパイラ」は、自然言語を一回投げれば必ず同じbytesが出るという保証ではありません。内部では推論・探索・修復・検証を反復してよく、外部に約束するのは**確定仕様に対する、証拠を伴う納品結果**です。矛盾や未許可の意味変更が必要になれば、影響範囲を保留して共同定義へ戻します。

**到達確認案：** 対象システム種別を限定して、共同定義から納品まで成立する。改修では既存データ・契約・手編集との差分を扱い、不要な全再生成ではなく検証可能な差分更新を行える。仕様確定は、本番配備や追加費用への無制限の許可ではありません。

<a id="web"></a>
## 6. HELIX-Web：初期はConnector型AI開発SaaS

### 6.1 「自分のVSCodeで行っている開発」をWebへ

目指す初期体験は、自分のPC・WSL・VPS・リポジトリ・AI利用環境をWebから操作できることです。最初から全コード・認証情報・計算資源をSaaS側へ移す必要はありません。[U08][U09]

```text
ブラウザ
   ↓
HELIX-Web：プロジェクト・操作・進行・利用者権限のサービス面
   ↓
Connector：接続、適格なPackの導入・確認、job受渡し、証拠返却
   ↓
ユーザーのPC／WSL／VPS／許可されたクラウド環境
   ├─ リポジトリ・Git・開発データ
   ├─ 導入済みDevelopment Packageと必要基盤
   └─ 公式に許可されたAI実行経路／ローカルLLM
```

Connectorへ各開発engineを重複実装するのではなく、検収済みPackageを選んで利用する方向を取ります。Webは操作面とサービス責務を担い、各開発契約の意味や既存の認可・独立検収を置き換えません。

### 6.2 認証方式は、提供するプロバイダーごとに決める

「自分のAI契約・ログインを使いたい」はUX上の方向性です。**ローカルの公式クライアントで使えることと、第三者SaaS経由で同じ利用枠を使ってよいことは、同じ確認事項にはしません。** 対応経路・利用条件は接続実装前に確認し、未対応の経路を対応済みとして表示しません。

初期の設計方針は、秘密情報を必要以上にWebへ移さず、利用者環境側で認証を扱える経路を優先することです。認証情報を置かない場合でも、コード・ログ・prompt・artifactに機密が含まれ得るため、何を返送するかは別に制御します。サブスクリプション利用、API、クラウド認証、ローカル推論のどれを使うかは未決定です。

MCPは接続手段の候補です。長時間job、切断、取消、再開、lease、証拠転送までをどう扱うかは、既存HELIX契約と必要な通信要件から決めます。MCP採用も新プロトコルの全面新設も、このビジョンだけでは確定しません。

### 6.3 HELIX-Web 3：開発支援（HELIX Developer Assistance）

Web3の明示的な節目は、**HELIX Developer Assistance（HDA）**です。チューニングしたLLMを分散サーバーから呼び出し、設計・実装・検証・レビュー・診断などの開発補助へ供給します。[U14]

```text
HELIX 3.0：データ → 調整 → 評価 → 採用したモデル成果
                                  ↓
                     適用範囲・版・評価証拠
                                  ↓
HELIX-Web 3 / HDA：適格なモデルを分散サーバーから呼び出す
                                  ↓
                      利用者・開発Agentを補助
```

モデルを育てる責務と、モデルを稼働させて応答を届ける責務は分離します。学習用と推論用の資源を同一視せず、配置、同時実行、遅延、費用、可用性、データ配置を実測で決めます。「ローカルLLM」は手元PC一台だけに置くという意味には限定しません。

HDAの応答は、必要な品質・安全検証を通る提案や作業結果です。低費用・高速化は狙う効果であって、特定の規模・精度・原価の達成をここでは約束しません。

<a id="autonomy"></a>
## 7. 主役は利用者：自分で保守し、改修できること

第三軸は機能追加の副産物ではなく、サービスの中心価値です。利用者がコードを直接書く必要はなくても、**何を変えるか、何を許可するか、どの結果を受け入れるかの主導権**を持てる状態を目指します。[U17]

| 自立の段階案 | 利用者の行動 | 開放前に必要な確認 |
|---|---|---|
| 定型保守 | 診断、設定変更、検収済み更新、復旧を選ぶ | 対象の一意性、許可範囲、停止・取消・回復、操作後の観測 |
| 案内付き改修 | 変更したい内容を伝え、影響と選択肢を確認する | 要求差分、プレビュー、移行、回帰、既存ユーザーへの影響 |
| 専門AIによる補助 | HDAを使って設計・検証・診断・改修を進める | モデルの適用範囲、根拠、不確実性、独立検収 |
| 知能による改修計画 | 目的から専用の改修フローを組ませる | 必須義務、人間判断点、再計画時の権限と証拠 |
| 差分再コンパイル | 画面・振る舞い・仕様を変えて新版を受け取る | 既存データ保全、意味差分、納品検収、配備・rollback条件 |

1.xから限定保守を始める、2.xで案内付き改修へ広げる、といった配置は検討できます。ただし、時期は固定しません。改修全般を一つの難易度で扱わず、例えば表示文言の変更と不可逆なデータ移行を別々に検収します。

5.0の理想は次の循環です。

```text
今のシステムを使う
  → 変えたい画面・振る舞いを示す
  → HELIXと意味・影響を確認する
  → 確定した差分仕様で再コンパイル
  → プレビュー・検収
  → 許可された更新・配備
  → 利用結果を見て、また育てる
```

納品した後も仕様・設計・実装・運用の対応を残すことが、次の改修の入力になります。保守会社や専門家を一切不要と保証するのではなく、利用者が自分で判断・実行できる範囲を広げ、残る専門判断を明確にします。

<a id="factory"></a>
## 8. HELIX-FACTORY：別の収益経路が並行して生まれる

HELIX-Webは、HELIXの能力をAI開発SaaSとして届ける一事業です。HELIX-MARKETINGや、その後に作るアプリ・サービスは別の商品として成長してよい。Coreの大きな節目を待たず、利用できる開発能力で事業を進める構想です。[U18][U19]

| 展開先 | 利用者への価値 | 収益化の検討対象・未確定事項 |
|---|---|---|
| HELIX-Web | 自分の環境とAIを用いた統制付き開発 | 利用形態、チーム、実行管理等。価格・課金軸は未決定 |
| HELIX-MARKETING | 市場・顧客・施策・利用を踏まえた判断と実行 | 対象業務と提供範囲。独立サービスの形・価格は未決定 |
| HDA等のモデル提供 | 検収した専門モデルによる開発補助 | 提供形態、推論量、専用配置等。品質・費用・権利が前提 |
| その他の製品・アプリ | 各市場・顧客の課題解決 | 企画ごとに採否を決める。SaaSに限定しない |

上表は収益化の候補であり、すべての商品化や収益性を保証するものではありません。工場としての強みは商品数そのものではなく、**次の商品を作るときに、実証済みの開発能力と提供資産を再利用できること**です。再利用率や削減率を架空の数字で置きません。

製品ごとの顧客・データ・要求・版・運用責任は分けます。事業が同じHELIXを使うことは、顧客情報や学習データを共有してよいことを意味しません。

<a id="marketing"></a>
## 9. HELIX-MARKETING：市場から作り、利用から直す

HELIX-MARKETINGは、作った後の集客だけを担当するものではありません。市場や顧客の課題から「何を作るか」を考える上流入力と、利用ログから「何を改修するか」を考える下流入力の両方を持つ構想です。[U20][U21]

```text
市場・競合・顧客の課題
  → マーケティング側で根拠付きの機会・製品仮説を形成
  → 企画・要求形成
  → HELIXによる開発・検証・提供
  → 市場投入・利用
  → 利用／顧客／運用の証拠
  → マーケティング側で問題・仮説・改修候補を形成
  → 正規の開発経路へ再入
  → 改修版の効果を観測
```

### 9.1 二種類の改修入口を区別する

運用側は、障害、接続異常、性能、設定driftなどから修復を求めます。マーケティング側は、利用・離脱・継続・問い合わせ・顧客反応などから、体験や価値の改善を求めます。両者の相関を調べることはあっても、一つのログから同じ原因だと決めつけません。

市場の需要、獲得施策、コンバージョン、製品内の利用、顧客対応、技術運用も、同じ指標へ潰さずに接続します。実測、欠測、推定、予測、原因仮説を分け、観測だけで要求変更を確定しません。

### 9.2 接続するのは、改修の「根拠」と「目的」

初期接続は、マーケティング側からHELIXの要求受付へ、根拠付きの変更提案を渡す形を想定します。正式な新schemaの採番は後段へ残し、最低限何を受け渡すかを構想として保持します。

**受渡し内容の案：** 対象製品・機能・Release、観測sourceと期間、対象顧客／segment、症状と期待成果、仮説と反証条件、代替案、変更候補、費用・リスク、必要な人間判断、変更後の観測方法。

マーケティング側は「初回利用を完了できない人が増えている」と根拠付きで提案できますが、直ちにDBや認証を変更する権限は持ちません。HELIX側で要求差分、UX、構造・実装・運用のどこに戻るべきかを評価し、必要な部分を人間と確認します。施策変更で解ける課題まで必ず開発案件にしません。

成熟後は、開発側からRelease・変更内容・観測対象を返し、マーケティング側が効果を確認する双方向接続へ広げます。通常ログの機械照合を起点とし、根拠が足りない場合だけ追加調査・再現・限定実験を選びます。全案件への総当たりA/Bテストは前提にしません。[U24]

### 9.3 製品改修とHELIX自己改善を分ける

製品の利用率が低いことは、そのままHELIXの欠陥を意味しません。まず対象製品の課題として扱い、要求の取りこぼしや検証漏れなどHELIX側の改善に結び付く証拠がある場合だけ、別の改善候補として還流させます。原文・観測・判断・変更・結果をつなぎ、因果が未確定なら未確定のまま残します。

<a id="crossings"></a>
## 10. 本体とサービスは、節目ごとに交差する

同期させるのは同じ版番号ではなく、**利用可能と確認した能力と、その利用結果**です。以下は同期を具体化するための設計案です。[U10][U11]

| 交差点 | 本体から渡すもの | サービス側で成立させるもの | 戻す材料 |
|---|---|---|---|
| Release Pack | 開発能力、最小依存、版、検収証拠 | Connectorへの導入・互換性・更新／撤去 | 導入・更新・利用上の問題 |
| 遠隔実行 | 許可scope、作業契約、結果・停止再開の契約 | Web操作、利用者権限、通信・断線・取消の扱い | 実行結果、失敗、待ち時間、介入 |
| 外部推薦 | 出典・適用条件付きの候補 | 案件に応じた提示、採否、追加検証への入口 | 採否理由と適用後の結果 |
| モデル／HDA | モデル・adapter・適用範囲・評価証拠 | 分散配置、適格な呼出し、応答品質・費用管理 | 品質、手戻り、遅延、失敗・反例 |
| Intelligence | 動的計画・根拠・必要義務 | 人間判断点、委任、計画変更の表示・操作 | 完了・停止・再計画の結果 |
| System Compiler | 仕様と検証付きの納品能力 | 共同定義、検収、保守・差分更新の体験 | 納品後の問題と変更要求 |

```text
HELIXの能力を改善
  → 対象scopeで独立検収
  → サービスが採用する構成へ束縛
  → 限定利用・観測
  → 提供範囲を拡張
  → 許可された証拠をHELIXへ還流
  → 次の改善
```

サービスが採用するPackage／Slice、Connector、モデル等の版とdigestは、構成のlockとして追跡する案です。既存の構成管理を再利用し、新しい意味正本を増やすことを目的にしません。WebのUI変更だけで、無関係な本体やモデルの版まで一斉更新しないようにします。[B02]

**版の分離方針：** 本書の文書版、本体の公開版、サービス版、接続契約版、選択Package／Slice／Bundleの版、モデル・datasetの版、環境適用revision、能力世代評価を区別する。同じ公開実体のPackageとBundleには、形式だけの二重バージョンを設けません。

本体3.0とWeb3のHDAは能力の受渡しとして対応しますが、同日公開・同一patch番号・全機能一斉更新を義務化する意味ではありません。

<a id="trust"></a>
## 11. 成長しても変えない境界

以下は、既存v0.6の分離原則と今回の未来構想を接続するための**設計原則案**です。新しいruntimeの実装済み宣言ではありません。[B01][B02][B03]

| 境界 | 維持すること |
|---|---|
| 品質と安全 | 要求を満たしたかと、行為・到達範囲を許可できるかを別に検査する。 |
| 推論と権限 | 知能は計画・候補を作る。自分で権限を拡大し、独立検収を省略しない。 |
| 人間と自動化 | 価値・趣向・表現・許可拡張等の判断点を残す。委任範囲内の技術判断を毎回の全面承認へ戻さない。 |
| 再確定の範囲 | 新要求・矛盾は影響範囲を特定して戻す。無関係な仕事の再freezeや停止を一律に求めない。 |
| 候補と実働 | 文書・code・接続・実証・公開を別に扱う。推薦や学習モデルも同じ。 |
| 製品とHELIX | 製品の改修とHELIXの自己改修を別対象にし、同じ正規開発能力を用いる。 |
| 配布と内部成長 | 必要な開発能力だけを渡す。成長機構の停止・未導入を通常開発の一律停止条件にしない。 |
| 公開と環境適用 | 成果物の検収、公開認可、本番配備、運用健全性を別に確認する。 |
| 不確実性と再実行 | 不明・欠測を成功へ変換しない。副作用の結果が不確実なとき、無条件で再実行しない。 |

### 学習とデータ利用の境界

サービスを使ったことは、コード・会話・利用ログを横断学習に使ってよいという同意ではありません。利用目的・権利・対象範囲を確認し、個別プロジェクト内での利用、事業内の改善、横断的な知識化、モデル学習を分離する方針とします。

外部OSS・文書・レビュー、第三者モデルの出力も、取得できることを再配布・学習・蒸留の許可と同一視しません。具体的なデータ源・モデルを採用するときに利用条件を確認します。秘密情報、個人情報、非公開oracle、無関係なプロジェクト情報を通常の学習入力へ混ぜないようにします。

生物比喩では、経験から残す適応情報をGene、状況に応じた利用を発現、計画退役をアポトーシスと捉えられます。ただし、これは設計の説明語彙です。既存のRequirement／Contract／Knowledge IDを置き換えず、学習・遺伝についての生物学的な事実主張にも用いません。[U25]

<a id="execution"></a>
## 12. 実行順序：今は構想を残し、1.0を使って磨く

**今、未来の仕組みを無理に実装する必要はありません。HELIX 1.0を使ってWebやMARKETINGの並行開発を磨き、その実践から接続を育てる。これを推進方針とします。**[U22]

| 時点 | 進めること | このビジョンだけでは進めないこと |
|---|---|---|
| 1.0まで | 既存範囲の収束、Packageの必要境界、未来の接続点の記録 | Webの新規統合、巨大な学習基盤、全体知能、全事業共通基盤の前倒し |
| 1.0以降 | HELIX本体とWebを二本進行。MARKETING等も別案件として本格的に磨く | 各案件の全機能完了を相互の一律前提にすること |
| 最初の接続 | 小さい提供範囲・対象環境でRelease PackとConnectorを検収。MARKETINGは根拠付き提案の受渡しから | 生ログの無制限共有、無承認の自動改修、全製品の一括切替 |
| 実証後 | 受渡し、効果観測、モデル提供、動的計画へ段階拡張 | 文書上の未来版を理由に、未検収能力をサービスへ公開すること |

既にあるHELIX-MARKETING等の構想や成果を停止・破棄する指示ではありません。1.0以前は必要な独立作業を続けられますが、深い統合や新たな必須依存を本体へ強制しない、という区別です。

並行開発では、独立した要求・責務・branch・作業範囲・検証を持ち、共有部分の競合、計算資源、レビュー待ち、停止再開を観測します。並列数だけを増やして速度向上と扱わず、手戻り・実時間・消費・人間の監視負担を含めて評価します。

接続を磨く順序は、**読める → 提案できる → 許可された変更を渡せる → 結果を確認できる → 検収済み範囲を広げる**です。これは導入の考え方であり、既存workflowを一律に置き換える新しい五工程ではありません。

<a id="qualification"></a>
## 13. 進化を何で確かめるか

機能数、Issue数、モデル数、生成コード量だけでは進化を認定しません。対象と測定範囲を決め、以下のような証拠で判断する案です。閾値・母集団・観測期間は未設定であり、導入前に決めます。

| 評価軸 | 観測するものの案 |
|---|---|
| 開発成立 | 要求に対する受入結果、検証漏れ、手戻り、回復性、納品後の問題 |
| サービス成立 | 導入・接続成功、job終端、切断・取消・再開、更新・撤去、利用者の操作負担 |
| 利用者の自立 | 専門家の介入が必要だった箇所、自分で完結できた保守・改修、失敗からの復帰 |
| 推薦・学習 | 根拠の妥当性、適用可否、保留の適切さ、採用後の効果・副作用、反例への対応 |
| 知能・コンパイル | 生成した計画の実行可能性、義務保持、再計画、仕様変更の識別、差分更新の成立 |
| 事業展開 | 実際の利用価値、継続利用、提供コスト、運用負担、次の製品への実証済み再利用 |

**「実装できた」「つながった」「役に立った」「安全に任せられた」「事業として成立した」は別の到達点**です。同じscoreへ平均して達成扱いしません。

## 15. HELIXの物語

**1.0で、開発を成立させる個体を作る。** そこから本体とWebの二本の進行が始まり、Release Packを通じて開発能力を利用者の環境へ届ける。

**2.0で、世界の開発経験を自分の現在地へ翻訳する。** サービスはその能力を利用者の案件へ届け、実践の結果を次の改善へ返す。

**3.0で、経験をモデル能力へ定着させる。** HELIX-Web 3のHDAが、調整したモデルを分散サーバーから呼び出し、現場を補助する。

**4.0で、HELIX自身が開発方法を組み立てる。** 育てたモデル群と既存の開発契約を使い、状況に応じた仕事の進め方を構成する。

**5.0で、人間と決めた仕様を、システムとして届ける。** そして納品後も、利用者が自分の意思で保守し、改修し、再生成できる。

その横ではHELIX-FACTORYが事業を生み、HELIX-MARKETINGが市場と利用の声を開発へ戻す。HELIXを育てることと、HELIXで価値を作ることが、互いの次の一歩を支えます。

> **作って終わるAIではなく、作ったものと、作る力の両方を、世代を超えて育て続けるHELIX。**
