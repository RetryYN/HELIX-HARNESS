# HELIX 開発コスト削減・判断軽量化・段階自動化 — 共通指示書

版1.0｜2026-09-08 JST｜対象：RetryYN/HELIX-HARNESS
原資料：投資候補一覧v1.0、INV-001〜072。原資料の照合mainは83a0ab069f0ab7d90151df6ad236a08c25073534。本書作成時の現行HEAD・実装状況は再監査していない。

## 1．目的と実行範囲
不要な作業を消し、定型判断・計算・転記を機械へ移し、検証済み経験を再利用して、同じ品質条件で受入まで完了する仕事の総費用と足踏みを減らす。AIには未知の意味判断、設計、反証、独立検収を残す。

本書は72投資候補を実施へ移す段階別指示であり、72新要求の承認・一括実装・v1分母追加ではない。P0〜P4は導入帯で、障害重要度P0/P1、既存M0〜M5、Release Waveとは別軸。後続研究をv1完成条件へ逆輸入しない。

## 2．最初に行うこと
選択対象についてだけ、最新main、要求ID/revision、承認範囲、IR、実装・consumer・既存PLAN/PR、現役writerを照合する。関連Issue番号は接続候補であり、存在だけで実装・承認済みとしない。

既存ownerへ次のいずれかとして接続する。
- 既存要求の実装・接続／意味不変の改善：既存の変更・検収経路で進め、一律再承認しない。
- 意味・受入・公開境界の改訂：差分だけ正規の要求改訂へ送る。
- 未定義の自動適用対象・契機・権限：追加差分を明示し、必要な承認・正本化・当該IR後に有効化する。
- 既に実用済み／不要／将来研究：証拠、理由、再評価契機を残す。既存要求を勝手に免除しない。

72件の初期照合を順次記録するが、全件調査完了を最初の改善やCI/Cursor運用の前提にしない。文書内INV IDを新しい恒久正本や72個のIssueへ自動変換しない。

## 3．段階と同時着手
P0即効・観測14件 → P1限定実装29件 → P2接続・差分化20件 → P3知識投資5件 → P4研究4件。各数は候補数であり同時実装数ではない。

原則は一責務枠一主作業、初期配分はC1/C2/G1/G2/R1の2:2:1。総資源には独立reviewを含める。検収・CI・統合が詰まれば新規PR投入より未完作業の収束へ回す。全員をこの投資開発へ移さず、v1本線・重大修復・Cursor実案件を維持する。

段階全体ではなく必要な入力能力で開始可否を判定する。各依存には、必要能力・提供元・有効版・検証証拠・未充足理由を付ける。既存能力で満たせれば後続段階の投資完成は待たない。段階順と能力依存が食い違う場合は、shadow/設計を先行し、必要な最小sliceだけ前倒しする。

## 4．実装と自動化の順序
観測 → check/dry-run/proposal → 隔離環境で限定適用 → 独立検証・実consumer → 認可済み範囲の常用 → 効果確認 → 対象拡大と旧経路移管。

既に検証済みの機構へ不要な再実験を課さない。新しい実行権限はこの指示書から推測しない。生成・診断・提案・適用・検収・公開を別状態にする。prepare/verify等は能力名であり、実在するCLI名・引数・挙動を確認して再利用する。

既存graph、event/receipt、DB projection、Authoring/Recovery、scheduler、実行adapterへ接続する。万能Bot、新DB、新承認engine、新schedulerを並立させない。担当の主ownerは選択sliceごとに一つ決め、独立検収は分離する。

## 5．必ず保持する境界
有効要求・scope・認可・独立review・必須検証は維持する。候補HELIXが自分を認可する経路、承認/証跡の補作、Guard解除、無許可force push/merge/publish/削除、他者未commit差分の破棄は禁止。学習・提案は実行権限を持たない。

patch/digest一致は意味同一の万能証明ではない。base、依存、環境、失効を確認し、未知時は必要範囲の調査・検証へ戻す。cacheや生成器の共有を独立oracleの代替にしない。合法入力の完走・失敗後の停止/再開/担当交代も試す。

## 6．測定と通過
baseline/candidate、対象HEAD、環境、義務集合、観測窓を束縛し、成功・失敗・timeout・未収束をすべて記録する。受入済み仕事一件に至る試行全体の実費、tokens、利用枠、人手、CI時間、到達時間、再作業、誤拒否、重大見逃しを別軸で比べる。欠測はnull、便益の二重計上は禁止。

採否基準と実験上限を先に決める。品質条件未達は拡大しない。費用削減目的なら移行・維持・再資格・復旧・運転費込みで改善を確認する。安全上必要な修復は金銭だけで否定せず、効果未測定を削減達成としない。

選択したsliceの正規main到達、必要な実consumer、停止/復旧、旧経路の扱い、比較証拠が揃って限定常用とする。モデル試験・文書化・Issue closeのみでは実用完了にしない。不要な任意分析は停止でき、通常開発の安全機構は残ること。

## 7．提出・引継ぎ
各INVに採否、現在の実装/利用状態、owner、要求差分、接続先、最初のslice、実入力依存、権限、検証証拠、実測、残義務、再評価契機を付ける。段階の報告は採用済み集合とその検収状態を分け、72件を固定の完成率分母にしない。

保存は一式、AIへの読込は本共通指示＋作業中の段階＋選択INVカードだけにする。全72本文を毎sessionへ投入しない。詳細カードがなくても本書の共通境界は有効だが、未確認の個別範囲を推測して実装しない。

## 投資の採否と実装状態を分ける
採否はcandidate/adopt/defer/reject/no_changeなど既存で利用可能な語彙へ写す。実装状態・利用状態・効果測定状態は別軸で持ち、採用されなかった候補を実装済みへ計上しない。これらの語彙を新しいruntime enumとして直接追加する指示ではない。

既承認要求を免除する場合は、投資候補のno_changeではなく、その要求の正規変更手続きが必要。対象縮小や受入変更は黙って行わない。

## 各sliceの最低提出内容
INV ID、対応要求ID/revision、主owner、既存実装/入口、採否、必要な意味・権限差分、最小scope、許可write-set、入力能力と証拠、独立検証、実consumer、前後比較、旧経路移管、失敗/撤回、残義務を提出する。

実費とサブスク枠は分ける。受入一件総費用には未成功試行も含める。受入がゼロなら単価をゼロや恣意的な数値にせず未定義として扱う。並列jobの合計runner時間と壁時計時間を分け、計測処理そのものの維持費も記録する。

金銭軸の純便益は、回避できた実費から自動化の運転・維持・再資格・復旧費を引く。一時的な実装/移行費は別記する。正の純便益と比較条件が確認できた場合のみ回収期間を推定する。安全上必要な修復は金銭便益ゼロでも必要になり得る。

## 段階移行の判断
「P1全29件が終わったらP2」という門は作らない。選択INVごとに入力能力の充足と現行認可を確認し、既存の検収・利用条件を満たしたら次のsliceへ進む。未充足は提供元、必要証拠、担当、再照合契機を明記する。

必要入力を供給できない場合も、無関係な前段・後段を止めない。研究成果は研究完了であり、製品適用は別検収。各段階の再予測は実績と残義務から行い、この資料は納期や削減率を確約しない。
