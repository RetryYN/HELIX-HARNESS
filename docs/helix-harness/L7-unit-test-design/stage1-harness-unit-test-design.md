## 2. Fixture規則と型付き期待

- 各行はL8の`CASE-HARNESS-L8-*`を一件だけ参照する。基準入力、単一変異またはpositive control、主結果、構造assertionをL8各cellと同じ内容で保持する。差異が出た場合は固定L8 cellが正本である。
- L7関数IDはL5の10 API候補に固定し、API引数/戻り型を増やさない。複数API fixtureはL8に記された順に複数FNを記載する。L6/L7が直接扱う共通kernel契約はK1/K2/K3/K5に限る。K6 `RequiredResult`等、K7 generation pointer/`EpochToken`はopaque owner境界として分離・保持し、内部動作の合格を主張しない。K4/G3は製品層の参照でありこのpairの詳細対象ではない。
- 主結果はL8に記された既存K1 result class/reasonまたはL5構造化`Value<T>`候補をassertする。domain field mismatchはpayload内field comparisonであり、K1 `Negative`、K2 `Stale`/`Unknown(conflict)`ではない。
- L8のlocal holdはそのままholdとし、独自reasonや新owner resultを補わない。K1 `Unknown` reasonはL4 Common Kernel §2.3の閉集合に従い、L8の固定入力で指定されたclass/reason/evidenceをそのまま保持する。`Unknown(unsupported)`は各caseがstub非対応入力として明示した場合だけで、一般既定値ではない。`K2 Stale`はcurrent lookupの既存動作、K3/K5/K6 resultはそれぞれのowner型を保つ。
- expiry relationは`before | equal | after`を比較payload内に保持する。equalのA/B predicateは未選択のままとし、いずれもexpiry後success count=0というL9 NFR条件を保持するが、実dispatch/effectの実行・証拠は作らない。
- authority source、dependency source、clock、dispatch/effect等は合成refか既存owner boundary stubだけを使う。owner実装を実行・代用したと主張しない。K3はcandidate refからcurrent owner/sourceを再読する既存境界、K5は既存event/result型の参照に限る。K6のreceipt verifierとK7のgeneration pointer/`EpochToken`内部動作は本pairで検査しない。HARNESSのpack/operation state・revision・expiryをK7で判定しない。
- output mutationのfixtureはAPI入力を固定し、test harness内でbaseline API payloadと比較用candidateの差を検査する。変異candidateを実API出力/入力として扱わない。
