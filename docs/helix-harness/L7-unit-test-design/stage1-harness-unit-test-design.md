## 2. Fixture構成規則

- 各test caseは`CASE-HARNESS-L8-*`を一行だけ読み、そのL8行をfixtureの正本にする。基準入力、単一変異またはpositive control、期待値はそのL8行のcellどおりとする。下表は対応を示す索引としてcellを再掲する。表示に差があればL8を正本とする。
- 各行は独立したtest methodとimmutable inputにする。API欄が複数候補を含む行は、記載順にL6候補を呼ぶが、L8 fixtureとL9 oracleの所属数は各一件とする。
- 各assertionはL8が定めるfieldと既存result class/reasonを確認する。L8がmappingを局所未確定としている箇所では`DomainEvaluation`のfactまたはownerへのhandoffを確認し、新しいK1 reason/result classを作らない。
- source/permission/record-reader/OS operationの入力は合成owner observationまたはstubに限る。network、credential、物理reader/writer、dispatch、release、旧runtime/test/CI、外部serviceを起動しない。
- K2 `Stale`はcurrent exact lookupがprior `Value`を選んだ場合だけassertする。`Unknown(conflict)`は同一identity/revisionの候補にdigest conflictがある場合だけassertする。製品field mismatchは`DomainEvaluation.Mismatch`として確認し、K2 classへ変換しない。
- fixtureがその境界を明示するときだけ、K7 generation pointer/`EpochToken`入力を境界として扱う。pack/operation revision、resume、expiry、idempotencyはHARNESS/OS fixture内のassertionに留める。
