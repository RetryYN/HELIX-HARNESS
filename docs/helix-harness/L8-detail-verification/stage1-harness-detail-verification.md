# HELIX-HARNESS Stage 1 L8詳細検証設計

本書は[L5](../L5-detail-design/stage1-harness.md)の製品契約を固定L10の12 functional case、5 NFR case、親別business boundary 3件の計20件へ展開する。下の`IV-HARNESS-*`は既存L9で定義済みのverifier IDであり、L8が再定義・再採番するIDではない。L8は各verifierが使うfixture候補とfield単位の変異方法を詳述する。設計状態であり、実行、pass、実装、CI、releaseを示さない。

fixtureは合成pack declaration、dependency refs、caller input、version、authority ref、saved state、event/evidenceだけを使用する。実ネットワーク、実credential、provider、release/deployment、旧runtime/test/CIを起動しない。L9の期待oracle、既存K1–K10の型/key/reason契約、固定L3/L10以外の状態語を新設しない。未知・未観測・比較不能は影響する当該operationだけ非肯定とし、全製品や全Stageを停止する新gateを作らない。

## 2. Fixture一覧（固定L9 verifier 20件を保持）

固定L10 source caseを入力境界として、各fixtureはAPI、正常基準、単一変異またはpositive control、期待値または局所保留を一行に記す。各L9 verifier IDは既存のまま維持し、fixture IDだけを識別子として加える。複数field、状態軸、source側とcaller側を同時に変えない。期待するAPI型はL5の候補APIと現行共通kernelの境界に限る。`Observed<T>`の`T`をL5が特定していない箇所では構造体やdomain結果型を新設せず、variant/reasonを局所保留する。構造体観測の不一致を`Value("mismatch")`等の文字列値へ変換しない。domain内のpack/dependency/scope/state field差をK2 key差へ読み替えない。K2の`Stale`はcurrent `lookup`で旧`Value`が返る場合、`Unknown(conflict)`はK2候補集合の同一identity・revisionに異なるdigestがある場合に限る。D1–D15はNFR-C-HARNESS-023-01の固定source fixtureを各々維持し、同じinput/revisionを2回評価する。D08のsource missingとstaleは別fixtureに分ける。旧assetの保持・変更理由とsource pinはL5 §2の12件を参照し、旧consumerがあるとは主張しない。

個々のAPIが返すvariantはL5または既存K1/K3に明記された範囲だけ固定する。ここでいうpack/capability/contract/dependency/scope/authority fieldの`mismatch`やnested refの`stale`は各source/domain値の照合結果であり、それだけでK2 `Unknown(conflict)`やK2 lookup `Stale`を作らない。K2のconflict/Staleは既存key lookup条件が独立して成立するときだけoracleにする。具体variant/reasonが上流にない行は同じAPIの非肯定境界を確認しつつ、そのresult mappingだけ局所保留する。この表は設計fixtureであり未実行である。実ネットワーク、credential、provider、release/deployment、旧runtime/test/CIは使用しない。
