# HELIX-HARNESS Stage 1 L8詳細検証設計

本書は[L5](../L5-detail-design/stage1-harness.md)の製品契約を固定L10の12 functional case、5 NFR case、親別business boundary 3件の計20件へ展開する。下の`IV-HARNESS-*`は既存L9で定義済みのverifier IDであり、L8が再定義・再採番するIDではない。L8は各verifierが使うfixture候補とfield単位の変異方法を詳述する。設計状態であり、実行、pass、実装、CI、releaseを示さない。

fixtureは合成pack declaration、dependency refs、caller input、version、authority ref、saved state、event/evidenceだけを使用する。実ネットワーク、実credential、provider、release/deployment、旧runtime/test/CIを起動しない。L9の期待oracle、既存K1–K10の型/key/reason契約、固定L3/L10以外の状態語を新設しない。未知・未観測・比較不能は影響する当該operationだけ非肯定とし、全製品や全Stageを停止する新gateを作らない。

## 2. Fixture一覧（固定L9 verifier 20件を保持）

固定L10 source caseを入力境界として、各fixtureはAPI、正常基準、単一変異またはpositive control、主結果、構造/owner assertionを記す。各L9 verifier IDと既存236 fixture IDは保持し、追加fixtureは個別IDにする。複数field、状態軸、source側とcaller側を一つの変異へ混ぜない。主結果欄はL5で定めた型候補または既存owner APIが返す型を記す。完全読取済みの純比較fixtureはL5の構造化比較payloadを持つ`Value<T>`、既存の非`Value` inputは同じclass/reason、owner結果はその既存型、意味/owner境界が未定義の箇所だけを局所保留とする。各行の主結果がこの三分類のどれかを示し、構造/owner欄には比較対象field、非昇格、ownerへ渡す候補refなどを明記する。構造体観測の不一致を`Value("mismatch")`等の文字列値へ変換しない。domain内のpack/dependency/scope/state field差をK2 key差へ読み替えない。K2の`Stale`はcurrent `lookup`で旧`Value`が返る場合、`Unknown(conflict)`はK2候補集合の同一identity・revisionに異なるdigestがある場合に限る。D1–D15はNFR-C-HARNESS-023-01の固定source fixtureを各々維持し、同じinput/revisionを2回評価する。D08のsource missingとstaleは別fixtureに分ける。完全読取した閉路/矛盾自体は`ClosureObservationCandidate`の比較値であり、closureを許す/拒否するpolicyだけが未確定である。旧assetの保持・変更理由とsource pinはL5 §2の12件を参照し、旧consumerがあるとは主張しない。

完全に読めた入力に対する純比較は、L5 §3.2の構造化payloadを持つ`Value<T>`として期待する。fixtureの期待結果は、(1)純比較`Value<...Candidate>`、(2)既存K1/K2/K3/K6 owner resultまたはinput classの保持、(3)未定義の意味/owner結果だけの局所保留、のいずれかに分類する。ここで`Value`は比較結果を観測したことを表し、pack適格、受入、Positiveやrelease eligibilityを意味しない。domain fieldの`mismatch`はpayload内の比較事実であり、K1 `Negative`やK2 `Unknown(conflict)`ではない。比較対象のsource input自体が既存`Unknown(reason)`、`Unobserved(why)`または`NotApplicable`ならそのclass/reasonを維持する。純比較以外の製品APIでL5が外側variant/reasonを定めない場合は主結果を「局所保留」とするが、構造/owner assertionは検査する。ここでいうpack/capability/contract/dependency/scope/authority fieldの`mismatch`やnested refの`stale`は各source/domain値の照合結果であり、それだけでK2 `Unknown(conflict)`やK2 lookup `Stale`を作らない。K2のconflict/Staleは既存key lookup条件が独立して成立するときだけoracleにする。主結果classを固定しないのはsourceの非`Value`入力または製品owner/authorityが返却意味を固定していない箇所であり、純比較の技術表現不足とは区別する。この表は設計fixtureであり未実行である。この3 API（`prepare_pack_invocation`、`resume_invocation`、`resolve_dependency_closure`）の残る局所保留は、K3 queryを構成するauthority候補ref自体が無くK3呼出しを作れない場合、dispatch後の実effect/resultが不確実で純比較を越える場合、human delegationの有効性/receipt owner判定、解決不能cycleに対するclosure policy、固定親のbusiness owner境界、または選択source/clock等の必須owner observationを取得できず既存型への具体写像が固定されない場合に限る。これらは主結果の意味を新設しない境界であり、同じ表の純比較payload結果や既存`Unknown(reason)` inputを置換しない。実ネットワーク、credential、provider、release/deployment、旧runtime/test/CIは使用しない。
