## 2. 共通fixture規則

`resolve_security_case`の戻り値は固定parent/case/refを解決できた`ResolvedSecurityCase`、または必要key/refを構成できない`Rejected(missing_key)`である。このresolver自身はK1 `Unknown`や`Value(Negative)`、K3 `PermissionCheck`を返さない。各fixtureの期待欄は、resolverが`ResolvedSecurityCase`を返した後に表のL5 projection APIが返すcomponentの期待を記す。source refが解決され値だけが不明ならresolverはResolvedのまま下流componentが既存Unknownを保持する。必須refがない場合はRejectedとなり下流projectionを呼ばない。`project_permission`は常に`PermissionCheckResult | PermissionCheckDiagnostic`の既存unionを返し、K3診断`missing_key`をK1 Unknownへ読み替えない。

各fixtureは一行の既存L9 verifier IDに対応し、親・AC・L10 CASE・owner戻し先を固定する。変異は同じfixture内で意味を混ぜず、fieldごとのnegativeを独立にする。source/owner completenessはcurrent owner declarationと実際に追跡できるproducer graphで照合する。参加者の自己申告、入力の省略、0 producerからcompleteを推定しない。未登録sourceまたは完全性を証明できないgraphはUnknown。missingの実読確認とunobservedを区別する。

positiveは当該操作の必要な固定source、current owner binding、該当K1/K2/K3/K6/K7/K8状態が肯定の場合だけである。K3 permission positiveはassignment、Worker実行、物理enforcement、business resultを肯定しない。K6 digest/reproductionはissuer authenticityを証明せず、`Unknown(unsupported)`を保つ。K7/G5のrecipient状態はownerごとに読む。not-appliedは適用を実観測して確認した結果であり、unobservedは適用証拠がない状態である。

## 7. 未確定・実行境界

OS assignment source、実producer graph、015/016 asset adapter、physical enforcement observation、G5 recipient declarationの一部はcurrent owner source上で実解決できるか未確定である。source未登録は`Unknown(unregistered)`、読取不能は`Unknown(unreadable)`、値を定められない入力は該当fixtureで固定した既存`Unknown(reason)`、未読・未実施は`Unobserved(not_run)`とする。完全scope読取で必要source/fieldの不存在を確認した場合だけ既存ownerのdomain-field absenceとして記録し、K1に`missing` classは作らない。必須`SubjectRef`/API key field自体の欠落は`Rejected(missing_key)`とし、下流projectionを呼ばない。保存済みK2 `Value`だけが過去keyに結び付く場合はK2の`Stale`規則を使い、新しいcurrent K3 queryの確定軸不一致をStaleへ読み替えない。該当case/operation/recipientだけを保留し、無関係親へ波及させない。実secret、実credential、実network、実resource、実保存、旧runtime/test/CIの実行は行わず、本pairはL4/L9 oracleに対応する未実行設計である。
