## 2. 共通fixture規則

`resolve_security_case`はL4 `resolve_security_stage1_case`の短縮adapter名であり、戻り値は`Observed<ResolvedSecurityCase> | Rejected(missing_key)`である。resolver rejectionは必須key/refを構成できない場合だけであり、解決済みsliceのUnknown/Unobservedは`Observed` payloadに残す。このresolver自身はK3 `PermissionCheck`を返さない。各fixtureの期待欄は、resolverが`Observed<ResolvedSecurityCase>`を返した後に表のL5 projection APIが返すcomponentの期待を記す。source refが解決され値だけが不明ならresolverはObserved payloadを返し、下流componentが既存Unknownを保持する。必須refがない場合はRejectedとなり下流projectionを呼ばない。`project_permission`は常に`PermissionCheckResult | PermissionCheckDiagnostic`の既存unionを返し、K3診断`missing_key`をK1 Unknownへ読み替えない。

各fixtureは一行の既存L9 verifier IDに対応し、親・AC・L10 CASE・owner戻し先を固定する。変異は同じfixture内で意味を混ぜず、fieldごとのnegativeを独立にする。source/owner completenessはcurrent owner declarationと実際に追跡できるproducer graphで照合する。参加者の自己申告、入力の省略、0 producerからcompleteを推定しない。未登録sourceまたは完全性を証明できないgraphはUnknown。missingの実読確認とunobservedを区別する。

positiveは当該操作の必要な固定source、current owner binding、該当K1/K2/K3/K6/K7/K8状態が肯定の場合だけである。K3 permission positiveはassignment、Worker実行、物理enforcement、business resultを肯定しない。K6 digest/reproductionはissuer authenticityを証明せず、`Unknown(unsupported)`を保つ。K7/G5のrecipient状態はownerごとに読む。not-appliedは適用を実観測して確認した結果であり、unobservedは適用証拠がない状態である。
