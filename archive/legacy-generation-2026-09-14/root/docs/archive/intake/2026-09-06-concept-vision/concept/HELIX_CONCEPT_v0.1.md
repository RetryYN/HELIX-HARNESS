# HELIX CONCEPT

## 経験を受け継ぎ、つくる力を進化させる。

**コンセプト文書 v0.1｜2026年9月6日**  
連携文書：HELIX VISION v0.1／開発Packageカタログ v0.6

> 作ったシステムだけでなく、作るために得た知恵も、次の世代へ残す。  
> 守るべきものを守り、変えるべきものを変え、役目を終えたものは安全に手放す。  
> HELIXは、その循環を開発の構造にする。

HELIXは、**システムを開発する能力と、その能力自体を育てる仕組みを持つ、継承型の開発システム**を目指す。生物学の語彙で表すなら「開発生命系」である。ただし、生命・意識・生物学的な遺伝を実現したという意味ではない。

本書は「なぜこの構造を取るのか」を説明する思想文書である。「どこへ進むか」はVISION、機構のカテゴリーと提供境界はカタログ、実行可能な約束は既存の要求・設計・契約が担う。生物名によるコードの改名、新しい実装階層、要件承認、公開資格を本書だけで発効しない。[V01][C01][C02][C03]

<a id="origin"></a>
## 1. 原点 — いいシステムは、世代を超えていく

> 「いいシステムって世代を超えてくことだよな？」

これがHELIXの出発点である。単に生物に似た名前を付けたかったのではない。開発者、AIモデル、実行環境、製品の版が変わっても、役に立った経験と判断の根拠を失わず、次の仕事へ渡せるシステムを作る。その考えが、生物学の継承・分化・適応という発想につながった。[U01][V01]

前世代の `RetryYN/ai-dev-kit-vscode` のREADMEにも、**Bio-engineering meets V-model**、設計とテストの対、細胞・器官・個体、恒常性、免疫という対応が記されている。生物学は後付けの装飾ではなく、初期の設計言語だった。[R01]

本コンセプトはその原点を受け継ぎ、役割を整理し直す。前世代の `Gene＝PLAN` は歴史的な対応として残すが、本書では、対話で示された **「Geneは経験側にあり、それらが集まって発現する」** を継承モデルの中心に置く。過去の語彙を無言で上書きせず、何を受け継ぎ、何を再解釈したかを付録に残す。[U02][R01]

HELIXにとって、長く残るべきものは必ずしも同じコードではない。要求の意味、確かめ方、失敗した条件、採用しなかった理由、利用者との約束である。実装を置き換えても、その資産を次へ渡せることを重視する。

<a id="principle"></a>
## 2. 生物を再現するのではなく、成長の原理を借りる

生物学から借りるのは、全機構を一対一に模倣する設計図ではない。**分けて働くこと、境界を保つこと、経験を選んで残すこと、環境に応じて働き方を変えること、不要な構造を回収すること**を、ソフトウェア設計の問いに翻訳する。

| 借りる視点 | HELIXで問うこと |
|---|---|
| 分化 | この仕事の責務は何か。隣の責務へ何を渡すか。 |
| 恒常性 | 変化の中でも、どの約束・権限・稼働条件を保つか。 |
| 継承 | 次の仕事や次世代へ、何を根拠付きで残せるか。 |
| 発現制御 | 今の案件で、どの能力・知識を、どの範囲で使うか。 |
| 選択と適応 | 何が役立ち、何が効かず、何を撤回すべきか。 |
| 再構成と退役 | 能力を失わずに、どの構造を置換・終了できるか。 |

ここには生物そのものとの違いもある。HELIXは、人間が定めた目的、利用者の権利、品質、安全、費用の制約の中で改善を選ぶ。自然淘汰をそのまま実装するのでも、無作為な変異を大量に試すのでもない。経験を継承可能な情報へ変換するのは、**人間が設計する検証・採用・版管理の仕組み**である。

生物名は理解を助けるために使う。意味が曖昧になる場所では、GeneよりKnowledge、免疫より操作認可、発現より実行契約という技術語を優先する。比喩によって責務を増やさず、実際の契約を隠さない。

<a id="helix"></a>
## 3. 二重らせん — つくる約束と、確かめる証拠を対にする

DNAの二重らせんは、相補的に結び付いた二本の鎖という構造を持つ。HELIXではこの形を、**要求・設計の約束と、それを確かめる検証を切り離さない姿勢**の象徴として用いる。[BIO01]

```text
つくる側の約束                   確かめる側の義務・証拠
目的・期待価値     ←─ 対応 ─→     利用・運用での結果
要求・受入条件     ←─ 対応 ─→     受入の判断根拠
設計・責務・契約   ←─ 対応 ─→     境界・状態・失敗の検証
実装・変更         ←─ 対応 ─→     実行されたテスト・独立検収
```

この図は説明用の対応であり、既存Vモデルの工程番号を再定義するものではない。**テスト件数を設計件数と等しくすれば正しさが証明される、という意味でもない。** DNAの塩基対やChargaffの規則から、ソフトウェアの検証十分性が導けるわけではない。

HELIXで大切なのは、要求や設計を原子的な検証義務へ結び、対象の版・内容・条件に合う証拠で確認することだ。試験項目が書かれていることと、その試験が実行され成立したことを分ける。変更後に古くなった証拠は、以前の成功というだけで使い回さない。[C01][C03]

「つくる」と「確かめる」を一緒に残せれば、後継の開発者やモデルは、コードだけでなく**何を壊してはいけないか**も受け取れる。二重らせんの象徴を、世代を超える開発資産へ結び付けるのはこの点である。

<a id="body"></a>
## 4. 身体の構造 — 開発する系と、自分を育てる系

HELIX本体は、全体統制の下に共通基盤・開発統制・成長統制を置く。この骨格は生物用語へ置換するために作り直さず、既存の整理を維持する。[V01][C03]

```text
HELIX本体
└─ 全体統制
   ├─ 共通基盤
   │  └─ 識別・正本／権限・証拠・履歴・共通契約・実行接続
   ├─ 開発統制
   │  ├─ 進行・配車・停止再開
   │  ├─ 要求形成・設計・実装・変更統合
   │  ├─ 品質保証
   │  ├─ 安全保証
   │  └─ 製品リリース・配備・運用保守・診断回復
   └─ 成長統制
      ├─ 自己観測・評価
      ├─ 改善・構造再編の候補化
      ├─ 経験・知識の継承と適用
      └─ HELIX自身の提供・更新・成長評価
```

**開発統制**は対象システムを作り、確かめ、届け、維持する。**成長統制**は、その開発能力が実践でどう働いたかを観測し、改善と継承を扱う。成長側がHELIXの変更を必要としたら、同じ正規の開発経路へ戻す。自己成長専用の無検収な書換え経路を作らない。

全体統制は全身の整合を保つ役割として捉えるが、全ての権限を独占する巨大な中枢にはしない。要求の採否、作業の認可、品質の検収、公開・配備の許可は、それぞれの責務が持つ。共通基盤を使うことも、データや権限の無条件共有を意味しない。

### 4.1 細胞・組織・器官は、構造を読むための補助語彙

| 比喩 | 本書で説明する対象 | 固定しないこと |
|---|---|---|
| Cell／細胞 | 境界、入出力、状態、責務を持つ機能単位 | 1関数・1ファイル・1Agentとの一対一対応 |
| Tissue／組織 | 関連する機能単位の協調 | ディレクトリ名や技術レイヤーとの一致 |
| Organ／器官 | 複数の責務が協調し、まとまった働きを担う機構群 | Package数と器官数の一致 |
| Organ System／器官系 | 複数機構による目的別の活動系 | 全枝へ同じ深さの階層を挿入すること |
| Organism／個体 | 自らの要求・状態・運用境界を持つ一つのシステム | 1サーバー・1プロセス・1リポジトリとの一致 |

これは機能の主所属を理解する補助であり、導出、利用、検証、遷移、所有を全て親子関係へ変換するものではない。HELIX自身も開発対象の一システムとして扱えるが、稼働中のHELIX、改修候補、利用者の製品は別の対象として識別する。

<a id="gene"></a>
## 5. Gene — 経験から残す、継承可能な適応情報

本書でいう **HELIX Gene** は、経験に由来し、適用範囲と検証根拠を持ち、後続の仕事へ受け継ぐ対象となった適応情報である。ユーザーの「経験部分が集まって発現する」という考えを、技術的に扱えるように整理した定義案だ。[U02]

生物学上のgeneは遺伝の基本単位である。一方、HELIX Geneを生物のDNAと同一視しない。開発経験が生物の遺伝子へ直接書き込まれると主張するものではなく、ここでは**経験を検証して継承する工学的な仕組み**に名前を借りている。[BIO02]

### 5.1 経験とGeneの間には、選抜がある

```text
実案件・レビュー・障害・運用の経験
   ↓
何が、どの条件で、どう起きたかを証拠へ結ぶ
   ↓
再利用できそうな判断・対処・規則の候補
   ↓
適用条件・反例・独立検証・利用権限を確認
   ↓
継承対象のGeneとして扱う
   ↓
次の仕事で必要なGene群を選び、利用する
   ↓
結果と副作用を観測し、資格・範囲を再評価する
```

この流れは概念上の整理であり、新たなruntime状態名ではない。既存のKnowledge、Pattern、VERIFY、promotion等との対応を使う。単発の成功も価値ある経験として残せるが、それだけで全案件に効く一般規則にはしない。

**Geneはログのコピーでも、正解文の寄せ集めでもない。** 「この条件なら、何を確かめ、どう判断すると役立つか」という条件付きの知恵である。失敗、棄却理由、適用しない条件も継承する。頻繁に現れることやAIの自信だけでは資格を上げない。

### 5.2 Geneを説明するために必要な内容

| 観点 | 残す情報 |
|---|---|
| 由来 | 元episode、要求・変更・結果、出典と参照先 |
| 責務 | どの責務がこの知恵を所有し、何へ適用するか |
| 内容 | 判断、手順、回避策、検証の仕方と期待する効果 |
| 適用条件 | 対象、環境、版、制約、適用しない条件 |
| 根拠と反証 | 実行結果、独立検証、反例、未確認事項 |
| 継承資格 | local限定か横断利用可能か、利用許可、期限、失効条件 |
| 変更履歴 | revision、後継、統合・分割、撤回先 |

これは説明上の必要情報であり、既存データを複製するGene専用DBや新しい承認engineの設置を意味しない。必要な項目が既存の契約にあれば、それを参照する。

### 5.3 Genomeは「全ファイル」ではなく、継承構成として捉える

**HELIX Genome**は、その時点で継承対象としたGene群と、その版・関係・適用条件をまとめて捉える概念である。過去の全ログ、全PLAN、秘密情報、未採用の仮説まで含むものではない。利用時に全量をLLMへ注入することもしない。

実際の生物のgenomeはDNA全体を指し、単に遺伝子だけの集合ではない。本書のGenomeは、継承構成を説明するために範囲を絞った比喩である。[BIO03]

要求・契約は「何を満たすべきか」を定める。Geneは「経験上、どう進めるとよいか」を支える。経験から要求変更を提案することはできても、**Geneが要求や人間の決定を上書きする権限は持たない。**

<a id="expression"></a>
## 6. 発現 — 持っている知恵を、今の仕事へ働かせる

知恵を持つことと、適切に使うことは違う。HELIXが持つ能力や知識を毎回全て起動すればよいわけではない。対象の要求、責務、環境、費用、リスクに合うものを選び、その場の行為へ変換する。その過程を**発現**として捉える。

生物学のgene expressionは、遺伝情報が機能につながる過程であり、RNAの生成などを通じて調節される。HELIXでは、条件付きの知識がContext、判断支援、許可済みの規則、作業計画に具体化することへ、この視点を借りる。[BIO04]

```text
利用を許可されたGene群・能力群
     ＋ 今回の目的・責務・環境・制約
                 ↓
       適用範囲・競合・鮮度の照合
                 ↓
         必要最小限の発現構成
                 ↓
   Context／既存policy／作業計画／能力利用
                 ↓
      品質・安全・権限を確かめて実行
                 ↓
   観測された行動・成果・手戻り・運用結果
```

最後の実際の働きを、説明上の**Phenotype／表現型**と呼ぶ。能力一覧、ベンチマーク値、モデル名だけでなく、対象案件で何ができたかを見る。同じGene群を持っていても、入力や制約、実行環境が違えば、結果の評価は別に必要になる。

### 6.1 発現制御と知識改版を分ける

特定プロジェクトである知識を使わない選択と、知識そのものの内容変更・失効は別である。前者は今回の適用判断、後者は継承対象の見直しとなる。

この区別を説明する補助語として、Epigenetics／エピジェネティクスを使える。ただし、生物学でのDNA配列を変えない化学的修飾等の概念と、ソフトウェアの設定変更を同一視しない。正式な技術名は**発現制御・適用profile**とし、全ての設定をEpigenomeと呼び替えない。[BIO05]

### 6.2 組合せは、新しい検証対象になる

単独で有効だったGeneを組み合わせても、全体で有効とは限らない。短時間で反復する規則と、外部APIの負荷を抑える規則が同時に適用されるような場合には、優先順位・競合・適用範囲を確かめる必要がある。

ここでいう「発現」は、単なる検索結果の貼付けではない。**必要なものを選び、矛盾を抑え、現在の契約に従って作用させること**である。動的な組合せも既存の必須検証や安全条件を省略する理由にはしない。

<a id="boundaries"></a>
## 7. 恒常性と境界 — 止めることと、次へ渡せること

恒常性をHELIXへ写すなら、「何も変えないこと」ではなく、変更や障害の中でも、必要な約束と稼働条件を維持することである。全体統制は個々の処理を全て抱えるのではなく、責務と依存、変更の影響、停止・再開を対応付ける。

### 7.1 品質保証と安全保証は、別の働きである

**品質保証は、要求されたものが成立したかを確かめる。安全保証は、その対象・行為・到達範囲を許してよいかを確かめる。** 安全保証には免疫・膜・隔離という比喩を使えるが、品質保証全体を免疫と呼んで一体化しない。[C01][C03]

Guardは操作前の認可、Sandboxは実行中の隔離、出力検査は外部成果を受け取る入口として分ける。安全に動いた結果でも品質が不足することはある。品質試験に合格しても、未許可の秘密情報取得や本番変更が許されるわけではない。

過剰なGuardで正規作業まで止める状態は、説明上「自己免疫的な過剰反応」と捉えられる。ただし、この比喩からGuardを無効にする結論は出さない。正常な通過と危険な拒否を対で検証し、対象、権限、scope、隔離の判断を改善する。

### 7.2 分類の境界には、受渡しの条件がある

仕事の流れでは、作る側が終えただけでは次へ進めない地点がある。そこでは、受け取る側が新しい成立条件を確かめる。

```text
Workerの作業終了
   → 出力の安全検査
   → 独立した品質検収
   → 必要な最終receiptの成立
   → 親による成果受入
   → 変更統合
   → 製品リリースの検収・認可
   → 別途認可された環境適用
   → 稼働結果の観測
```

これは受渡しの説明図であり、全案件へ一律適用する新しい工程表ではない。**process終了、独立検収後のlifecycle terminal、親acceptanceは異なる**というv0.6の区別を保つ。[C01][C03]

各境界には、渡す成果、対象の版、必要な証拠、受け取る責務、不足時に止める範囲、戻す先、再開条件を持たせる。この境界の内側は、既存のcontract、object、状態機械、API、原子検証まで掘り下げる。細胞名やPhase名を増やすだけで階層を深くしたことにはしない。

### 7.3 恒常性は、全体停止の口実にしない

不足した証拠や未確定の変更は、影響する行為を止める。一方、影響を切り離せると確認した仕事は継続する。影響が不明なものを安全な独立作業と決めつけることも、何か一件未解決なら全て停止することも避ける。

正常な仕事を通すこと、危険な仕事を止めること、止まった理由と再開条件を示すこと。この三つを合わせて、統制の働きとする。

<a id="metabolism"></a>
## 8. 代謝 — 成長のために、通常の仕事を食い潰さない

HELIXにとっての資源は、計算機のCPU・メモリ・GPU、実行時間、トークン、外部サービスの利用枠、費用、そして人間の注意である。これらを観測し、仕事と成長活動へ配分することを、代謝の視点で捉える。

目標は、瞬間的に最多のAgentを走らせることではない。必要な品質と安全を維持して、仕事を継続できることだ。計算資源が足りなければ待機・直列化・再配置を選び、検証の省略で速度を作らない。予算に達したら未完義務と再開先を残し、曖昧な副作用を無条件に再実行しない。[C01][C03]

自己観測、学習、ベンチマーク、新機構の実験も資源を消費する。**成長のための仕事には、その必要性と予算が要る。** 通常開発より常に優先される特権は与えない。

開発Packageの利用に、その場での学習やHELIX全体の自己改善を必須にしない。供給済みの適格な能力を使って開発できることと、内部で新しい能力を育てることを分離する。これが「生き続けるための成長」と「成長のために仕事を止める状態」を分ける。

<a id="renewal"></a>
## 9. 再構成とアポトーシス — 成長は、増やすことだけではない

> 「リファクタリングはアポトーシスだな。」

この着眼を、**古い構造を安全に終わらせることも成長の一部である**という原則として取り込む。[U03]

ただし、意味を分ける。リファクタリング全体は、外から約束した振る舞いを保つ構造再編であり、全てが機構の削除ではない。その中で不要になった責務実装を計画的に終了する部分を、Apoptosis／アポトーシスになぞらえる。生物学でのアポトーシスはプログラムされた細胞死であり、単なる処理待機とは異なる。[BIO06]

| 呼び方 | HELIXで扱う仕事 | 代用しないもの |
|---|---|---|
| Remodeling／再構成 | 公開された意味・挙動を保ちながら、構造・依存・配置を整理する | 能力を削って軽くしただけの変更 |
| Regeneration／再生 | 障害からの復旧、または後継実装で必要な働きを回復する | 復旧しただけで根本原因も解消したという判断 |
| Apoptosis／計画退役 | 役割・利用者・移行先を確認し、不要機構を制御して終了する | fail-closeによる一時停止、無条件の削除 |
| Autophagy／内部回収 | 不要な内部構成物・一時資産を、保全義務に従って整理・回収する | 検証証拠、監査履歴、利用者データの無断破棄 |

オートファジーは細胞内の成分の分解・再利用に関わる仕組みであり、細胞全体の計画的な死と同じものとして扱わない。この違いを、**内部資産の回収と機構自体の退役を分ける**説明に用いる。[BIO07]

### 9.1 退役は「消す」の前から始まる

```text
現行機構と利用者・依存を確認
   → 維持／共存／置換の候補を比較
   → 必要なら後継と移行・回復手順を準備
   → 振る舞いと検証能力の低下がないかを確認
   → 利用者を移行し、必要な互換期間を扱う
   → 正規の権限で旧機構を退役
   → 残参照・設定・実行入口・配布物を照合
   → 必要な履歴と教訓を保全
```

旧機構がまだ使われるなら、年齢や名称、行数だけで削除しない。逆に後継が動いていても、旧呼出し・timer・設定・配布物が残れば移行は終わっていない。退役、移行、証拠の保全は、一つのdelete操作へ畳み込まない。

**コードは退役できるが、その機構が必要だった理由まで忘れない。** 旧機構の経験がGeneとして残れば、同じ失敗を別の名前で作り直すことを避ける助けになる。

<a id="adaptation"></a>
## 10. 適応 — 実践から選び、必要なものだけを残す

HELIXの成長は、「AIに改善案を出させ続けること」ではない。まず実作業のログと契約を照合し、再発、手戻り、検証漏れ、境界の不足、資源の圧迫などを発見する。その証拠から、通常の修正で足りるか、構造変更や新しい機構が必要かを考える。[U04][V01]

```text
観測 → 問題・改善機会 → 原因と影響の候補
                         ↓
       既存対処／構造再編／新機構の必要性を比較
                         ↓
             必要な範囲で反証・限定検証
                         ↓
               採用／不採用／保留
                         ↓
            正規開発 → 検収 → 限定適用
                         ↓
              効果・副作用・再発の観測
                         ↓
              知識・規則としての継承
```

通常ログで分かることを、毎回総当たりの比較実験へ戻さない。根拠が不足する場合に、追加観測、再現、比較、PoCを選ぶ。A/Bテストそのものを禁止するのではなく、**解くべき不確実性と期待価値がある場合に使う**。

採用しなかった案も理由を残す。同じ候補を何度も作って消費する循環を避けるためである。変更をmergeしたことと、利用上の改善が確認できたことも別にする。効果が消えたり反例が出たりしたら、適用範囲の縮小、再検証、降格・撤回へ戻れるようにする。

新しい機構を生み出すことは目的ではない。既存の契約や対処で解けない不足が根拠付きで示されたときだけ、創出を選ぶ。**成長の結果は、能力を保ったまま仕組みが減ることでもよい。**

<a id="intelligence"></a>
## 11. 神経系と知能 — 経験を読む段階から、開発方法を考える段階へ

HELIXでは、決定的な照合・状態管理と、AIの仮説・推論を組み合わせる。この協調を神経系の比喩で説明できるが、モデルを増やしただけで全体知能が成立するとは考えない。

本体の将来像はVISIONの節目を継承する。数字は能力の物語であり、公開版の互換性番号や生物学的な進化段階を意味しない。[V01]

| ビジョン節目 | 獲得する能力 | 生物的な読み方 |
|---|---|---|
| HELIX 1.0 | 定義した範囲の開発・検証・提供・運用を成立させる | 働き続ける身体と、その維持 |
| HELIX 2.0 | 外部の開発データを分解し、現在の案件へ根拠付きで推薦する | 外界の観測と、他者の経験の利用 |
| HELIX 3.0 | HELIXデータを使い、ローカルLLMを調整・評価できる | 経験を判断能力へ定着させる準備 |
| HELIX 4.0 | 調整したモデル群を使い、案件に応じた開発フローを動的に構築する | 状況に応じた行動・発現の構成 |
| HELIX 5.0 | 共同で要件を確定し、検証可能なシステムとして納品する | 仕様から個体を形成する発生・形態形成の比喩 |

3.0から4.0に向けて想定するのは、小型のローカルLLM群と、Kimi級の大規模な公開モデルの用途別チューニングである。ゼロから汎用基盤モデルを作る計画ではない。具体的なモデル・手法・計算資源・利用ライセンスは採用前に決める。公開重みとOSSの条件も一括りにはしない。[V01]

学習された重みは、Geneの原文や検証根拠の代わりにはならない。どのデータと設定からモデルが作られ、どの責務に適格かは外側に残す。知識の撤回が必要になったときに、モデル内からその情報を完全に消せたと推測することも避け、更新・再評価の方法を別に検討する。

4.0の価値は、固定フローを全て捨てることではない。既存のPackage、作業契約、検証義務、経験を使って、**今回の仕事に必要な流れを構成し直せること**である。4.0以前に動的な配車や部分合成が存在しないという主張にはしない。

### 知能と権限の境界

```text
Intelligence：こう進める候補を作る
       ↓
既存統制：目的・権限・依存・品質・安全を照合する
       ↓
Runtime：許可された行為を実行する
       ↓
観測・独立検収：結果を確かめ、次の判断へ返す
```

知能は委任された範囲で働く。自分の都合で権限を広げたり、独立検収を自己評価へ置き換えたりしない。この境界は知能化を妨げる付帯条件ではなく、知能を安心して使うための構造である。

<a id="packages"></a>
## 12. 分化と配布 — 身体を丸ごと渡さず、必要な開発能力を届ける

HELIXが内部に持つ全機構を、そのまま全利用者へ配布する必要はない。外部へ出す基本単位は、**対象システムの開発責務を実行し、利用可能な成果を受け取れるPackage**である。基盤も、その責務を成立させる最小範囲に絞る。[C01][C02]

要求形成、設計、実行、品質、安全、CI、統合、リリース、配備、運用保守、診断、リファクタリングといった提供責務は、v0.6のカタログを参照する。そこにある13候補を、13の生物学的器官や13の公開済み製品へ読み替えない。

| 整理する対象 | 役割 |
|---|---|
| Package | 利用者に約束する開発責務と成果 |
| Module | 既存責務・path・artifactの所有 |
| Functional Release Slice | 検証・昇格・更新・rollbackの単位 |
| Bundle／Profile | 選択した能力と依存を束縛する構成 |
| Artifact／Release Pack | 実際に渡す内容と、その版・検収根拠 |

この表は包含順序ではない。Moduleの所有とPackageの選択構成を分け、既存と同じ公開実体に二重の版管理を作らない。Release Packは、必要な能力を選んで渡す呼称として既存の構成・artifactを再利用する。[C02][V01]

HELIX全体の統治、自己評価、学習、機構創出、自己公開工程は、原則として内部に保つ。一方、対象製品の品質計測、CI観測、運用監視、利用許可済み知識の読取りは、その開発に必要なら提供できる。**学習する仕組みと、学習の成果を使う仕組みを分ける。**

これが初期HELIX-WebのConnector型サービスの布石になる。Webから利用者の実行環境へ、必要な開発能力を届ける。単独導入・更新・取消・撤去を確かめ、全体成長待ちで各Packageを止めない。

<a id="ecosystem"></a>
## 13. 生態系 — 本体・サービス・市場が、別々に育ちながら交差する

HELIX本体は作る力を育て、HELIX-FACTORYはそれを使って製品・サービス・事業を生み出す。FACTORYは事業群を捉える名称であり、全事業を束縛する巨大な共通DBや新runtimeを意味しない。[V01]

```text
HELIX本体 ── 適格な能力・成果 ──→ HELIX-FACTORY
   ↑                                  ├─ HELIX-Web
   │                                  ├─ HELIX-MARKETING
   │                                  └─ 製品・アプリ・その他事業
   └──── 利用が許可された経験・改善根拠 ─────┘
```

### 13.1 本体とWebは、1.0以降の二本の進行

1.0以降はHELIX本体とHELIX-Webが並行して進み、Release Pack、Connector、外部知識推薦、モデル提供などで交差する。Web展開は本体1.0〜2.5の進展帯に置く構想である。能力の受渡しと互換性で同期し、同じ版番号や同日公開には縛らない。[V01]

初期の体験は、自分のPC・WSL・VPS・リポジトリ・AI利用環境をWebから操作すること。どのログイン・利用枠を第三者サービス経由で扱えるかは、プロバイダーごとの確認が必要であり、Connectorを置けば自動的に許可されるとはしない。

HELIX-Web 3の**HELIX Developer Assistance（HDA）**は、調整したLLMを分散サーバーから呼び出し、利用者や開発Agentを補助する構想である。モデルを育てる仕事と、推論を届ける仕事は分ける。分散配置はデータや権限の境界をなくすものではない。[V01]

### 13.2 マーケティングは、市場と利用を開発へつなぐ

HELIX-MARKETINGは「作った後に売る」だけではない。市場・顧客の課題から企画を考える入口と、利用ログから改修を考える入口を持つ。[V01]

```text
市場・顧客の課題 → 製品仮説 → 要求・設計・開発 → 市場投入
        ↑                                      ↓
変更後の効果確認 ← 正規の改修 ← 利用・離脱・顧客反応の観測
```

技術運用の障害と、利用者の体験上の問題は別の観測として扱う。マーケティング側は根拠と期待価値を提案し、HELIX側はどの要求・設計・実装を変えるかを検討する。低い利用率から直ちに原因を断定したり、製品の問題を全てHELIX自身の欠陥にしたりしない。

### 13.3 継承するのは、利用許可を持つ知恵

サービスを利用したことを、コード・会話・ログの横断学習への同意とは扱わない。プロジェクト内の利用、事業内改善、他案件への知識継承、モデル学習は分けて許可を確認する。

共有された知見に価値があっても、元の利用者データや秘密情報をGeneとして横流ししない。外部データやモデル出力も、取得可能であることと再配布・学習可能であることを分ける。生態系という比喩は、所有・機密・権利の境界を薄める理由にはならない。

<a id="ownership"></a>
## 14. 主役は利用者 — システムを、自分の手で育て続ける

このコンセプトの到達価値は、HELIXが自分自身のために進化し続けることではない。**利用者が、自分のシステムを保守し、直し、必要な機能へ育てられること**である。[V01]

HELIX 5.0のSystem Compilerは、人間と画面・動作・要件を一緒に確定し、その後を検証可能な納品へつなぐ構想だ。画面から読み取れない費用、権限、データの扱いなどは必要に応じて確認する。納品後も変更したい意味を入力にし、既存データと契約を守りながら差分を生成する。

```text
使う → 変えたいことを示す → 意味・影響を確認する
                                  ↓
          既存の約束とデータを守って改修する
                                  ↓
       プレビュー → 検収 → 許可された配備 → また使う
```

この形成をMorphogenesis／形態形成として説明できるが、完全なシステムが無条件に発生するという意味ではない。内部で探索・再設計・修復を行ってもよい。約束するのは、対象として定めた仕様と納品条件に対する証拠である。

利用者が逐一コードを書く必要はなくても、**目的、価値、趣向、変更の許可、納品の受入を決める主導権は残す**。委任済みの技術判断まで毎回人間へ返すこととは区別する。保守・改修を利用者へ開く時期は、操作の難しさ、対象範囲、失敗からの回復性を実証して決める。特定の版への確約はしない。

生物の比喩を使っても、HELIXに自己保存や無制限な増殖を目的として与えない。止める、替える、使わないという利用者の選択も、システムの設計範囲に置く。

<a id="charter"></a>
## 15. 成長しても変えない、八つの原則

### 01｜継承は、コピーではなく根拠の受渡し

何を作ったかだけでなく、どの条件で成立し、何が失敗し、何を守るかを残す。履歴があることを、一般化の資格があることと混同しない。

### 02｜知恵の利用と、知恵の改版を分ける

今の仕事で選ぶことと、後続へ残す情報を変えることは別判断である。Contextの変更だけで長期知識やauthorityを書き換えない。

### 03｜つくる仕事と、育てる仕事を分ける

対象製品の開発とHELIXの成長を区別する。HELIXの自己改修も正規開発を使い、内部成長機構の停止で通常開発を一律停止させない。

### 04｜品質、安全、権限を相互に代用しない

試験合格は操作認可ではない。隔離成功は要求充足ではない。計画の良さは自己承認の根拠ではない。

### 05｜止めた理由と、次へ進める条件を残す

候補・保留・失効・未確認を成功へ変換しない。停止は必要な影響範囲へ限定し、再開に必要な根拠を示す。

### 06｜成長を、消費量と機構数で測らない

改善効果、回復性、手戻り、費用、人間の負担を確かめる。不要な実験、重複機構、無差別な記憶注入を成長と呼ばない。

### 07｜退役しても、必要な意味と経験を失わない

後継・移行・互換・証拠を確かめて古い構造を手放す。動いている能力の破壊と、計画的な退役を区別する。

### 08｜人間が、自分のシステムを育てられるようにする

HELIXの成長を利用者の自立へ結び付ける。所有、判断、データ、停止・移行の選択を、サービスへの依存で取り上げない。

## 16. 今の役割 — 未来を残し、実践から接続を育てる

今は、生物用語の数だけengineやテーブルを増やす時期ではない。HELIX 1.0の対象を収束させ、その開発能力を使ってWeb、MARKETING、各製品の並行開発を磨く。その実践から必要な接続と継承の条件を確かめていく。[V01]

本書の取り込みでは、既存契約に対応する説明と、本当に新しい要求が必要な差分を分ける。Gene、Genome、発現等はまず思想と対応辞典として置き、既存ID・owner・状態機械を置換しない。最新リポジトリの再監査や実装完了の認定は、本書の作成範囲ではない。

VISIONは未来の到達点を描く。CONCEPTは、そこへ向かうときに守る構造と判断原理を描く。カタログは、今どの責務・境界・提供案が整理されているかを示す。この三つを混ぜずに接続する。

> **作ったものを育てる。つくる力も育てる。**  
> **その経験を次の仕事へ、次のモデルへ、次の世代へ渡していく。**  
> **それがHELIXである。**

| Apoptosis | 不要機構の計画的な退役 | Gateによる保留や一時停止と区別する |
| Autophagy | 不要な内部資産の整理・回収 | 機構全体の退役や監査証拠の破棄と区別する |
| Regeneration | 必要な働きの回復・後継による再構成 | 復旧と根本解決を同じ完了にしない |
| Neural Adaptation | 経験をモデルの判断能力へ取り込む構想 | 生体神経の再現、意識、性能向上の保証ではない |
| Morphogenesis | 確定仕様から検証可能なシステムを形成する比喩 | 画面だけから全条件が一意に決まるとはしない |
| Ecosystem | 本体・サービス・製品・市場の相互作用 | 顧客・権限・データを無制限に共有しない |
| Generation | 継承と能力変化を見る視点 | 文書版、SemVer、観測系列、既存G評価と混同しない |
