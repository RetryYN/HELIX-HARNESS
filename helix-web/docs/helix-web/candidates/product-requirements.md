# HELIX-Webの要求候補（2026-09-26 PO原案）

## これは何か

2026-09-26にPOが示した「HELIX-Web製品群 要求原案」のうち、HELIX-Webが担当する部分を、原文のID・種類・文言のまま載せる。
原文の状態は「要求候補・未採択」である。本書は要求（L2）でも受入（L11）でもなく、本書から要求の採用・承認・実装許可を生成しない。
採択後は、対象の`L1-planning/`、`L2-requirements/`、`L11-acceptance/`へ対応させる（原案1.2）。

### 1．製品構成・命名・文書配置

#### 1.1 製品と機構の所属

以下の個別製品の英字識別名は、本原案で定義する文書上の名前とする。

| 識別名 | 分類・所属 | 提供するもの |
|---|---|---|
| **HELIX-Web** | Web提供系の製品総称 | 製品群全体の利用体験・構成体としての価値 |
| **HELIX-WEB-HARNESS** | 開発系7製品の総称・統合提供 | 単独製品の利用と、製品間を接続した開発 |
| **HELIX-WEB-HARNESS-PROTOTYPE** | 製品① 画面プロト／PoC | 画面試作、実現性の検証、検証結果 |
| **HELIX-WEB-HARNESS-REQUIREMENTS** | 製品② 要件定義 | 要求形成、要件定義、受入条件 |
| **HELIX-WEB-HARNESS-DESIGN** | 製品③ 設計 | 構造編集、設計導出、設計書 |
| **HELIX-WEB-HARNESS-DEVELOPMENT** | 製品④ 開発 | 要求・設計に対応したコードと検証証拠 |
| **HELIX-WEB-HARNESS-REFACTORING** | 製品⑤ リファクタリング | 振る舞い・境界を維持した構造改善 |
| **HELIX-WEB-HARNESS-RELEASE** | 製品⑥ リリース | 配布物、配備の仕組み、更新・切戻し手順 |
| **HELIX-WEB-HARNESS-OPERATIONS** | 製品⑦ 運用保守 | 観測、診断、改修、復旧、継続改善 |
| **HELIX-WEB-HARNESS-CORE** | WEB-HARNESS配下の共通機構 | 顧客製品ごとの意味・設計・依存・変更の処理 |
| **HELIX-WEB-CONNECTOR** | Web提供系の接続製品 | 利用者のLinux環境・開発ツール・プロバイダーとの接続 |
| **HELIX-WEB-OS** | Web提供系の運転機構 | 顧客案件、工程、ジョブ、権限、提供版、サービス運転 |
| **HELIX-LABO／内蔵HELIX-Bench** | HELIX本体に所属 | 実績集計、比較評価、性能差吸収の検証、改善Feedback |

COREやWEB-OSを、WEB-HARNESSの8番目・9番目の製品として数えない。共通実装を利用することと、製品・案件・状態・権限の所属を同一にすることを区別する。

### 2．HELIX-Web全体の要求

**目的：利用者が自分の製品の構造を編集し、開発から運用保守まで継続し、その実績がHELIXの改善とWeb提供能力の更新へつながること。**

ID接頭辞：`HELIXWEB-L2-`  
既存の001〜009を別の意味へ流用せず、本原案では010以降を使用する。

| 番号・種類 | 要求 | 受入候補 |
|---|---|---|
| **010・構成体** | HELIX-Webを製品総称とし、WEB-HARNESSの7製品、WEB-CONNECTOR、WEB-OS、共通機構の所属と責務を識別できること。 | 製品、総称、内部機構、接続先を区別でき、全要求が単一の「Web機能」へ集約されていない。 |
| **011・構成体** | 本体の機構・実装・契約を再利用しながら、Web側の提供条件、受入、案件状態、権限、提供版を独立して管理できること。 | 共通機構の更新だけでWeb側の権限や案件状態が変わらず、Web固有差分を追跡できる。 |
| **012・構成体** | 各製品が必要な依存だけで単独利用・単独受入・単独リリースでき、組み合わせた場合は接続要求と構成体要求を満たすこと。 | 他の任意製品を無効にした構成でも単独受入できる。単体合格だけで統合合格にしない。 |
| **013・構成体** | Web上の入力・構造編集から、設計導出、作業生成、実装、検証、リリース、運用保守まで追跡できること。 | 入力変更から成果物・検証・稼働結果まで辿れ、画面の存在だけをサービス成立としない。 |
| **014・構成体** | 初期のHELIX実行環境を検証済みLinux構成に限定し、操作端末のOS、HELIXの実行OS、開発対象製品の動作OSを分離すること。 | Windows・macOSの操作端末であることだけを理由に利用不可とせず、対象製品の別OS検証は別に管理する。 |
| **015・構成体** | 利用者が保有するプロバイダー、モデル、エディタ、リポジトリ、実行資源を、対応範囲内で利用できること。 | 特定プロバイダーへの乗換えを暗黙に強制せず、未対応能力と代替条件を確認できる。 |
| **016・構成体** | 顧客製品の改善循環とHELIX本体の改善循環を分離し、評価した改善だけを提供版としてWebへ戻すこと。 | 顧客の一変更が共通知識・全顧客環境へ直接反映されない。 |
| **017・単体** | 公開統計の主題を、モデル順位ではなく、HELIXによる品質・時間・費用・手戻り・介入量の差の吸収とすること。 | 性能差が残る条件や悪化した結果も、改善した結果と同じ基準で表示される。 |
| **018・接続** | 公開統計はLABO内のHELIX-Benchが生成した公開用結果を利用し、非同期バッチの結果を日次で更新すること。 | Web独自の評価点を作らず、集計版、対象期間、締め時点、更新日時、遅延を表示する。 |

本体1.0の完成条件とWebの公開条件は分離する。7製品を要求対象から削除せず、初回公開に含めないものは対象と導入段階を明示して保持する。

### 15．製品間・本体間の接続要求

ID接頭辞：`HELIXWEB-L2-CONNECTION-`

| 番号 | 接続 | 要求・受入候補 |
|---|---|---|
| **001** | PROTOTYPE ↔ REQUIREMENTS | 試作・PoCの仮説、結果、採否、未解決事項を相互に渡すこと。仮説を確定要求へ無条件に昇格させない。 |
| **002** | REQUIREMENTS → DESIGN | 対象要求、制約、受入条件、合意revision、未決事項を渡すこと。設計側の不足発見を対応する要求へ戻せること。 |
| **003** | DESIGN → DEVELOPMENT | 設計、依存、入力契約、変更影響、検証義務を渡すこと。異なる設計revisionの証拠を混ぜない。 |
| **004** | DEVELOPMENT ↔ REFACTORING | コード、境界、維持する振る舞い、既存検証、構造差分を渡すこと。構造改善を理由に未承認の機能変更を混入させない。 |
| **005** | DEVELOPMENT／REFACTORING → RELEASE | 対象成果物、依存、テスト・レビュー、未完義務を渡すこと。必要な証拠が欠ける構成をリリース可能としない。 |
| **006** | RELEASE → OPERATIONS | 配備版、環境、監視条件、運転手順、バックアップ・復旧条件を渡すこと。配備後の責任と観測開始を確認できること。 |
| **007** | OPERATIONS → REQUIREMENTS／DESIGN／DEVELOPMENT | 障害・改修要求を必要な上流へ戻し、応急復旧と恒久改修を分離すること。修正後に元症状と退行を再確認すること。 |
| **008** | Web編集 → WEB-HARNESS-CORE | 型付きの編集操作を、案件・対象・元revision・操作IDへ束縛すること。無効入力、競合、権限外変更を誤適用しない。 |
| **009** | CORE ↔ BRAIN／INTELLIGENCE | 知識提供、適用判断、製品への確定を分けること。契約版、必要入力、代替、根拠、不確実性を往復させること。 |
| **010** | WEB-OS ↔ WEB-CONNECTOR | 実行対象・権限・予算・期限と、実行状態・結果・証拠を同じジョブへ結び付けること。切断を成功や未実行へ読み替えない。 |
| **011** | Web提供系 → LABO | 許可された観測だけを共通形式で渡すこと。データの出所、目的、対象版、観測時点、欠測、保持条件を維持すること。 |
| **012** | LABO内Bench → WEB-OS → 公開画面 | 公開用集計snapshotと評価方法の版を受け渡すこと。Web側で評価意味を変更せず、原評価と公開値の一致を確認すること。 |
| **013** | LABO → 本体OS → 改善対象機構 | Feedbackを登録・振分けし、対象機構の正規の変更経路で改修すること。LABOが要求・権限・提供版を直接書き換えない。 |
| **014** | 本体のリリース → WEB-OS | 製品・共通機構の版、依存、互換性、検証、移行・切戻し条件を渡すこと。提供能力の更新と顧客製品の更新を別操作にすること。 |

機構間接続ごとに契約と検証を持ち、汎用的な「接続済み」という一項目で全接続の成立を代替しない。

### 16．共通の安全性・データ・非機能要求

ID接頭辞：`HELIXWEB-L2-NFR-`

| 番号・種類 | 要求 | 受入候補 |
|---|---|---|
| **001・構成体** | 顧客・案件・環境ごとにデータ、状態、権限、資格情報、資源、証拠を分離すること。 | 他顧客・本体内部への越境参照や操作を拒否し、共有実装を越境の根拠にしない。 |
| **002・接続** | 利用者入力、外部資料、モデル出力を未信頼入力として扱い、認可や実行命令へ無検証に変換しないこと。 | 文書・ログ・生成物内の命令で権限・実行対象・秘密情報の扱いが変更されない。 |
| **003・構成体** | サービス提供、案件内評価、横断統計、汎用知識化、モデル学習、公開を別の利用目的として管理すること。 | サービス利用を包括同意へ変換せず、許可範囲外の二次利用を防ぐ。 |
| **004・構成体** | 原文、設計、ログ、集計、評価材料ごとに収集範囲、保持期間、削除、利用停止を扱うこと。 | 顧客の生ログ・秘密情報を公開せず、削除・利用停止が関連する処理へ反映される。 |
| **005・単体** | 少数案件の特定を招く集計や絞込みを抑制すること。 | 公開値の内部根拠は監査可能だが、公開画面から個別顧客データへ到達できない。 |
| **006・構成体** | 機構停止時に影響範囲を限定し、必要な義務を失わず継続・保留・停止を選べること。 | Bench停止で開発を全面停止せず、必要な認可・証拠が得られない処理は無理に継続しない。 |
| **007・構成体** | 操作応答、設計導出、ジョブ待機、同時利用、保存容量、復旧時間、データ損失範囲、費用・計測負荷を定義・測定すること。 | 対象workload・環境・測定方法と閾値を持ち、未測定を合格としない。具体数値は根拠をもって後続で確定する。 |
| **008・構成体** | ノード操作以外にも、フォーム・文章・一覧等で対象と変更内容を扱えること。 | 複雑な図の操作だけを必須にせず、入力不備や拒否理由を利用者が理解・修正できる。 |
| **009・構成体** | 保存・更新・復旧・配備・権限変更を追跡し、実行者、対象revision、許可、結果を確認できること。 | 操作者不明の変更、監査不能な復旧、失効権限での再実行を防ぐ。 |

### 17．HELIXの改善とWeb更新に関する構成体要求

ID接頭辞：`HELIXWEB-L2-COMPOSITE-`

| 番号 | 要求 | 受入候補 |
|---|---|---|
| **001** | 顧客の入力・人間の修正・AI提案・検証・運用結果を関連づけ、何が有効で何が修正されたかを評価できること。 | 修正回数だけでAIの失敗と決めつけず、要求変更、環境差、好み、実装不備等を分ける。 |
| **002** | 評価から改善対象をBRAIN、CORE、HARNESS、INTELLIGENCE、OS、CONNECTOR、SECURITY等へ振り分けられること。 | 一つの問題をすべてモデル性能の問題へ集約しない。 |
| **003** | 改善候補を比較・実験・独立検証し、適用条件と退行を確認してリリースできること。 | 動作したことだけを改善とせず、品質・時間・費用・介入・運用負荷を確認する。 |

| **006** | 新版適用後の実績を再びLABOへ戻し、改善効果と性能差吸収の変化を日次統計へ反映できること。 | 改善しなかった結果、退行、切戻しも観測・公開基準から除外しない。 |

### 18．主要な受入シナリオ

各行は、対応するL2要求群を通したL11受入候補とする。すべて未実行。

| シナリオ | 確認する内容 |
|---|---|
| **7製品の単独成立** | 各製品へ必要な入力だけを与え、他の任意製品を使わずに成果物と検証証拠を受け取れる。共通機構への依存は明示される。 |
| **ノード編集から設計変更** | DB項目を必須化すると、関連画面、API、既存データ、テストへの影響と判断事項が返る。ノード位置の移動だけでは意味が変わらない。 |
| **プロト・PoCから要求の再形成** | 試作・実験で得た結果を要求へ戻し、採用・棄却・未決を保持したまま設計へ渡せる。PoC成功を本番受入としない。 |
| **工程管理と完了予測** | 変更に伴い作業・検証・依存・予測が更新され、変動理由を示す。実作業、待機、再作業を区別し、予測誤差を後から確認できる。 |
| **Linux上での継続実行** | ブラウザーやネットワークの切断後も状態を保持し、再接続して確認・取消・再開できる。重複実行と失効権限の再利用が起きない。 |
| **既存作業との共存** | 利用者がエディタで行った変更とHELIXの変更を区別し、競合を扱える。利用者の変更を破棄せず、COREとの差を追跡できる。 |
| **リリースから運用・復旧** | 配備、監視、障害検出、対処、復旧、恒久改修、再発確認までを同じ製品・構成履歴で辿れる。 |
| **運用保守から知識化** | 成功例と失敗・復旧例を比較し、条件付きパターンを抽出できる。顧客固有情報を共通知識へ混入させない。 |
| **HELIX改善からWeb反映** | 改善を製品単位で検証・公開・切戻しできる。既存案件の参照版と設計は自動上書きされない。 |
| **性能差吸収の公開** | 同じ受入基準で品質差、時間、総費用、手戻り、介入を比較する。差が縮まらない条件や退行も示し、翌日の集計へ反映する。 |
| **集計障害からの復旧** | 集計が失敗しても顧客の開発を継続できる。公開画面は最終更新と遅延を示し、復旧後の再集計で二重計上しない。 |
| **情報・権限の分離** | 他顧客、権限失効、秘密情報を含む入力、少数集計を試し、越境・無断利用・再識別につながる公開が起きないことを確認する。 |
